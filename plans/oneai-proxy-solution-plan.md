# OneAI Proxy 详细方案与实施计划

> 文档状态：已复核方案基线 v0.2，可进入阶段 0  
> 编写日期：2026-08-27  
> 当前阶段：仅完成方案设计，尚未开始业务代码实现  
> 技术路线：Go + SQLite + Vue 3 + TypeScript，本地服务页面，后续可选桌面壳

## 1. 目标与决策摘要

OneAI Proxy 是一个面向单机用户的本地 AI 请求代理。它在 Codex、Claude Code 或其他兼容客户端与多个上游厂商之间提供稳定的协议转发、按优先级容灾、自动恢复、日志审计和统计分析能力。

已确定的核心决策如下：

1. 后端使用 Go，前端使用 Vue 3 + TypeScript，数据使用 SQLite。
2. V1 采用本地服务页面，不以 Tauri、Wails 或 Electron 作为核心运行方式。
3. Vue 构建产物嵌入 Go 可执行文件。普通用户安装或运行发布包时不需要 Go、Node.js 或 npm。
4. 支持三个独立协议入口，但不做跨协议转换：
   - OpenAI Chat Completions：`POST /v1/chat/completions`
   - OpenAI Responses：`POST /v1/responses`
   - Anthropic Messages：`POST /v1/messages`
5. 每个渠道只能属于一种协议。同一厂商如果支持多个协议，应配置为多个独立渠道。
6. 渠道按照路由组中的优先级依次尝试；先进行同渠道重试，再切换下一个渠道。
7. 连续失败阈值决定渠道何时进入冷却或系统自动禁用，不决定当前请求何时切换渠道。
8. 人工禁用、系统自动冷却和系统自动禁用必须分开；人工禁用的渠道不能被探针自动恢复。
9. 日志默认只保存元数据，完整请求与响应内容必须由用户显式开启。
10. 前端高保真复现 Anthropic 官网的视觉语言，但使用本项目自己的名称、图标、组件、文案和实现代码，不复制 Anthropic 的商标、专属字体文件、插画、视频或源码。

需要保留的官方兼容性边界：当前 Codex 官方自定义 Provider 配置中，`wire_api` 只明确支持 `responses`。因此本代理会提供 Chat 和 Responses 两种 OpenAI 协议，但 Codex CLI 的正式接入以 Responses 为基线；Chat 入口主要面向 OpenAI Chat 客户端、SDK 和其他兼容客户端。

三个 `POST` 入口是已确认的核心范围。阶段 0 还要捕获当前 Codex 和 Claude Code 的真实调用清单；如果客户端确实调用 Responses 资源查询/取消接口或 Messages `count_tokens` 等伴随接口，应按原协议补入 V1，并让资源 ID 延续原渠道亲和，不能把伴随请求随机发送给其他渠道。

## 2. 产品范围

### 2.1 V1 范围

- 三种协议的非流式和 SSE 流式转发。
- 渠道、路由组、优先级和能力声明管理。
- 全局模型映射和渠道级模型映射。
- 同渠道重试、跨渠道 fallback、连续失败阈值、冷却、半开和自动恢复。
- 主动探针、手动探针、启动探针和冷却结束探针。
- 请求日志、渠道尝试日志、健康事件、探针记录和配置审计记录。
- 当天、7 天、30 天统计以及渠道级延迟、成功率、缓存相关指标。
- 监听地址、端口、超时、重试、冷却、日志等通用设置。
- 渠道和相关配置的导入、导出、校验、差异预览和回滚。
- 浅色、暗色和跟随系统主题。
- Windows、macOS、Linux 的可运行发布包。

### 2.2 V1 不做

- Chat、Responses 和 Messages 之间的相互转换。
- OAuth 账号池、多账号轮询、计费售卖和配额分发。
- 多用户、组织、角色权限和远程公网管理。
- 任意 JavaScript/Lua 脚本改写请求。
- 基于权重、成本或实时延迟的智能负载均衡；V1 只按显式优先级顺序尝试。
- 桌面托盘、原生通知和强依赖桌面壳的功能。
- 直接复制其他代理项目的代码组织、数据库结构或实现。

### 2.3 后续版本候选

- `/v1/models` 聚合和上游模型发现。
- 渠道能力自动检测与模型级健康状态。
- Responses WebSocket 传输。
- 费用估算和价格表管理。
- 系统托盘、开机启动、原生通知和一键打开管理页。
- 诊断包导出、日志全文检索和更完整的失败原因分析。

## 3. 用户安装与使用方式

### 3.1 开发环境与用户环境

| 场景 | Go | Node.js | 说明 |
| --- | --- | --- | --- |
| 本地开发 | 需要 | 需要 | Go 编译后端，Node.js 构建 Vue 页面 |
| CI 发布 | 需要 | 需要 | 构建三平台产物并完成打包 |
| 普通用户安装使用 | 不需要 | 不需要 | 运行已经编译并嵌入前端资源的发布包 |

### 3.2 用户首次使用流程

1. 用户下载对应系统和 CPU 架构的发布包。
2. 首次启动时创建数据目录、SQLite 数据库、配置文件和本地管理凭证。
3. 服务默认只监听 `127.0.0.1`，不暴露到局域网。
4. 用户打开本地管理页，添加渠道并选择协议。
5. 用户配置渠道实际模型、逻辑模型、路由优先级、重试、冷却和探针。
6. 用户执行“试连”或手动探针，确认渠道可用。
7. 用户将 Codex 或 Claude Code 的 Provider 地址指向本地代理。
8. 后续请求由 OneAI Proxy 自动执行重试、fallback、冷却和恢复。

### 3.3 数据目录

默认使用操作系统约定的数据目录：

- Windows：`%LOCALAPPDATA%\OneAI Proxy\`
- macOS：`~/Library/Application Support/OneAI Proxy/`
- Linux：`$XDG_DATA_HOME/oneai-proxy/`，未设置时使用 `~/.local/share/oneai-proxy/`

目录内至少包含数据库、配置、备份和可选内容日志。命令行参数 `--data-dir` 用于便携模式和故障恢复。

### 3.4 V1 便携包运行闭环

- Windows 解压后运行 `oneai-proxy.exe serve`；macOS/Linux 解压后运行 `./oneai-proxy serve`。
- 便携版默认前台常驻，在控制台输出代理地址、管理地址、数据目录和停止方式；用户在浏览器手动打开管理地址，按 `Ctrl+C` 触发优雅停止。
- 同一数据目录通过进程锁保证单实例。第二个实例发现锁后输出已有实例信息并退出，不能并发打开同一 SQLite 数据库。
- 端口占用时明确报告冲突地址并退出，不静默改用随机端口。
- 便携版崩溃后不承诺自动重启；用户级服务、自启动和崩溃拉起由后续原生安装包提供。
- Windows 说明前台控制台窗口不可关闭；Linux 包保留执行权限并提供 `chmod +x` 故障提示；macOS 正式包必须完成签名和公证，否则只能标记为测试构建并说明 Gatekeeper 操作边界。
- 升级前停止接收新请求，等待活动请求或达到优雅退出时限，释放数据库锁并自动备份后再替换二进制。迁移失败时恢复数据库备份并保留旧版本可执行文件。
- CI 可以构建六个 OS/架构目标，但只有完成对应目标真实或等价硬件 smoke test 的产物才能标记“正式支持”，其余必须标记“实验支持”。正式公开分发要求 Windows Authenticode 签名、macOS 签名/公证以及全部产物 SHA-256 校验和。

## 4. 总体架构

```text
Codex / OpenAI-compatible clients / Claude Code
                         |
              Local proxy listener
                         |
              Protocol entry adapters
       +-----------------+-----------------+
       |                 |                 |
 OpenAI Chat       OpenAI Responses   Anthropic Messages
       |                 |                 |
       +--------- Request envelope --------+
                         |
             Model mapping + route plan
                         |
      Capability filter + priority ordering
                         |
      Retry / fallback / request time budget
                         |
         Channel health state + affinity
                         |
              Upstream protocol channel
                         |
         Request/attempt/probe event records
                         |
       SQLite + aggregation + log retention
                         |
               Admin API + Vue 3 UI
```

建议一个进程内提供两个监听器：

- 代理监听器：只承载 `/v1/*` 客户端请求。
- 管理监听器：承载管理页面、`/api/admin/v1/*` 和 `/healthz`。

两个监听地址和端口均可配置，默认都只绑定回环地址。代理令牌与管理令牌分离。这样即使未来用户主动将代理监听器开放到局域网，也不必同时暴露管理页面。

## 5. 领域模型与术语

| 术语 | 定义 |
| --- | --- |
| 协议 `Protocol` | `openai_chat`、`openai_responses`、`anthropic_messages` 之一 |
| 厂商 `Provider` | OpenAI、Anthropic、Azure 或第三方兼容服务，仅用于分类和展示 |
| 渠道 `Channel` | 一个确定的协议、上游地址、凭证、连接设置和能力声明 |
| 逻辑模型 `LogicalModel` | 本地用于稳定路由的模型别名 |
| 全局模型映射 | `(协议, 客户端模型) -> 逻辑模型` |
| 渠道级模型映射 | `(渠道, 逻辑模型) -> 上游实际模型` |
| 路由组 `RouteGroup` | `(协议, 逻辑模型)` 下的有序渠道列表 |
| 逻辑请求 `Request` | 客户端发起的一次请求，不因重试或 fallback 增加数量 |
| 渠道尝试 `Attempt` | 逻辑请求在某个渠道上的一次实际上游调用 |
| 探针 `Probe` | 独立于真实业务请求的渠道可用性检查 |
| 健康状态 | 系统根据真实请求和探针结果维护的自动状态 |
| 人工状态 | 用户显式启用或禁用渠道的管理状态 |
| 自动失败动作 | 渠道达到连续失败阈值后进入 `cooldown` 或 `auto_disabled` 的策略 |

模型解析顺序固定为：

```text
客户端请求 model
  -> 协议内全局模型映射
  -> 逻辑模型
  -> 查找对应路由组
  -> 按优先级得到候选渠道
  -> 各渠道的渠道级模型映射
  -> 上游实际 model
```

全局映射必须包含协议维度，禁止 Messages 的模型映射意外进入 Responses 路由。

## 6. 核心模块与接口接缝

采用“接口小、实现深”的模块设计。调用方只感知少量稳定接口，协议差异、重试细节、状态转换和存储实现保留在模块内部。

### 6.1 协议适配模块

三个 Adapter 分别负责：

- 识别 `model`、`stream` 和必要能力。
- 保留对应协议的原始 JSON 和 SSE 事件语义。
- 注入认证 Header、自定义 Header、query 参数和路径前缀。
- 只执行允许的同协议改写，例如模型名替换和固定字段覆盖。
- 解析上游错误、usage、缓存 token 和响应 ID。
- 判断流式响应何时进入“已提交”状态。
- 清除 hop-by-hop Header，且不把本地代理鉴权 Header 发送给上游。
- 不修改用户输入、system prompt、工具定义和多模态正文。

对路由模块暴露的核心接口概念为：

```text
Prepare(inbound request, channel target) -> prepared attempt
Execute(context, prepared attempt, event sink) -> attempt result
Probe(context, channel, probe policy) -> probe result
```

不会把 Chat、Responses 和 Messages 强行转换成一个统一的厂商请求对象。共享的是执行策略和观测事件，不是协议正文。

### 6.2 路由规划模块

输入协议、客户端模型、请求能力和可选亲和信息，输出有序候选列表。其内部完成：

1. 全局模型映射。
2. 路由组查找。
3. 人工禁用过滤。
4. `cooldown`、`auto_disabled` 等不可路由健康状态过滤。
5. 渠道能力过滤。
6. Responses 亲和渠道约束。
7. 按 `(priority, position, channel_id)` 进行稳定排序。
8. 渠道级模型映射。

应提供“路由模拟”能力：只展示映射路径、候选顺序、跳过原因和当前健康状态，不向上游发送请求。该能力有助于在正式请求前发现配置错误。

数据库约束、管理接口和导入校验都必须保证 `route_group.protocol == channel.protocol == global_mapping.protocol`。相同 `priority` 允许存在，但必须由路由组内唯一 `position` 和 `channel_id` 形成稳定的第二、第三排序，保证任何一次执行都按同一 A、B、C 顺序尝试。

### 6.3 容灾执行模块

容灾执行模块接收路由计划并隐藏重试细节，对外只返回最终结果和完整尝试账本。关键预算包括：

- 单渠道重试次数。
- 单请求最大切换渠道数。
- 单请求最大总尝试次数。
- 连接超时、首字节超时、流空闲超时和总请求超时。
- 客户端排队超时。

所有循环都必须受次数和时间双重预算约束，避免无限重试和重复计费。

策略取值顺序固定为“系统内置默认值 -> 全局配置 -> 渠道覆盖值”，后者只覆盖明确填写的字段。此规则适用于单渠道尝试次数、连续失败阈值、自动失败动作、冷却基数/上限、恢复成功阈值和自动恢复开关，路由模拟必须显示最终生效值及其来源。

### 6.4 健康状态模块

健康状态模块负责判定渠道是否可参与路由，并接收真实请求或探针结果。调用方不直接修改失败计数和冷却时间。

### 6.5 观测与存储模块

请求执行只发送结构化事件，不直接拼装统计 SQL。存储模块负责事务落库，聚合模块负责把原始事件汇总为小时桶和时间窗口指标。这样可以在清理正文或明细日志后继续保留 30 天统计。

## 7. 请求生命周期

### 7.1 普通请求

```text
鉴权和大小检查
  -> 协议识别与浅解析
  -> 全局模型映射
  -> 路由计划
  -> 选择最高优先级可用渠道
  -> 渠道级模型映射
  -> 在当前渠道执行 1 + N 次尝试
  -> 成功：记录结果并结束
  -> 失败：记录一次渠道级连续失败
  -> 未达到总预算：切换下一个渠道
  -> 全部失败：返回最后一个可解释错误和 request_id
```

### 7.2 流式请求

流式切换遵守一条不可破坏的规则：

- 向客户端输出第一个有效协议正文事件之前，可以重试或切换渠道。
- 输出有效正文事件之后，不再切换渠道，不拼接另一个上游的响应。

实现时需要区分“收到上游 HTTP Header”和“向客户端提交有效正文”。三种协议的提交点在阶段 0 固化成 Adapter 规则表，初始基线为：

| 协议 | 触发提交的首个事件 |
| --- | --- |
| OpenAI Chat | 第一个完整、合法、非注释、非 `[DONE]` 的 `data` JSON 帧 |
| OpenAI Responses | 第一个符合当前官方 Responses 事件样例的合法生命周期事件；具体允许事件名随兼容矩阵冻结 |
| Anthropic Messages | 合法的 `message_start` 事件 |

SSE 注释、空帧、ping 和 keepalive 不触发提交。首个有效事件前出现协议 `error`、非法帧、超时或断流时，按错误策略决定同渠道重试或 fallback。代理在提交点前不得向下游写 HTTP 状态、Header 或正文；默认最多缓冲 256 KiB 并受 `first_event_timeout` 限制，超过任一限制都按首事件前失败处理。提交后原样 Flush 已缓冲事件；之后发生错误只记录 `stream_interrupted`、结束连接并禁止切换渠道。

还必须处理：

- 客户端取消向上游传播。
- 下游断开立即取消上游请求。
- SSE 空闲超时和总时限。
- 有界缓冲和背压，禁止无限缓存响应。
- 服务关闭时停止接收新请求，并给予活动流可配置的优雅退出时间。

### 7.3 Responses 渠道亲和

当 Responses 请求包含 `previous_response_id` 时，优先查找本地保存的 `response_id -> channel_id` 关系：

- 亲和渠道可用时，只在该渠道上执行允许的重试。
- 亲和渠道不可用时，默认返回可解释错误，不能静默切换到不认识该 ID 的渠道。
- 用户可在高级配置中明确选择“允许无状态 fallback”，但默认关闭。
- 亲和记录有独立保留期，且不保存响应正文。

## 8. 重试、错误分类与健康状态机

### 8.1 错误分类

V1 即保留结构化错误分类，而不是把所有失败存成字符串：

- DNS、连接、TLS 和网络中断。
- 连接超时、首字节超时、流空闲超时、总超时。
- 401/403 认证或权限错误。
- 404 路径或模型错误。
- 408/409/429 等可独立配置的响应。
- 5xx 上游错误。
- 空响应、非法 JSON、非法 SSE。
- 上游在流开始前或开始后主动断流。
- 客户端取消和下游断开。

每一类错误都可以配置“是否同渠道重试、是否 fallback、是否计入连续失败、是否触发或延长冷却”。建议的 V1 默认值如下，用户仍可按错误类别覆盖：

| 错误 | 同渠道重试 | fallback | 默认健康影响 |
| --- | --- | --- | --- |
| DNS、连接、TLS、首事件前断流 | 是 | 是 | 计失败 |
| 408、429、500、502、503、504 | 是 | 是 | 计失败，并遵守 `Retry-After` |
| 401 或明确认证失败 | 否 | 是 | 进入配置错误/自动失败处理 |
| 403 | 否 | 是 | 由协议 Adapter 判断权限错误或暂时故障 |
| 明确的 model not found | 否 | 是 | 只标记该渠道模型不可用，不直接熔断整个渠道 |
| 本地已确认的 400/413/422 | 否 | 否 | 客户端请求错误，不影响渠道 |
| 上游普通 400/422 | 默认否 | 默认否 | 保留原错，避免盲目重试 |
| 客户端取消、下游断开 | 否 | 否 | 不影响渠道 |
| 流已提交后的上游断流 | 否 | 否 | 记录部分失败，不透明切换 |

错误策略必须集中定义并通过临时测试验证，不采用散落在 Handler 或 Adapter 中的判断。即使在流提交前重试，上游也可能已经计费；界面和文档必须提示重复计费风险，并在上游支持时透传或生成兼容的幂等键，但不能假定所有厂商都支持幂等。

### 8.2 连续失败的计数单位

同一逻辑请求在一个渠道上的全部重试耗尽后，才记为一次“渠道级连续失败”。单个 Attempt 不直接增加渠道失败连续值。成功的真实请求会清零真实请求连续失败值。

探针失败使用独立计数，是否影响真实请求健康状态由探针策略控制，避免一次低成本探针误杀正常渠道。

### 8.3 状态模型

人工状态与健康状态正交：

```text
admin_state: enabled | disabled
health_state: healthy | degraded | cooldown | half_open | auto_disabled
```

状态转换：

```text
healthy
  -> 渠道级失败但未达阈值 -> degraded
  -> 达到阈值且 failure_action=cooldown -> cooldown
  -> 达到阈值且 failure_action=auto_disable -> auto_disabled

degraded
  -> 真实请求成功 -> healthy
  -> 达到阈值且 failure_action=cooldown -> cooldown
  -> 达到阈值且 failure_action=auto_disable -> auto_disabled

cooldown
  -> 到期 -> half_open

half_open
  -> 探针或受控真实请求成功 -> healthy
  -> 失败 -> cooldown，并增加冷却级别

auto_disabled
  -> auto_recover=true 且探针达到恢复成功阈值 -> healthy
  -> auto_recover=false -> 等待用户手动重置自动状态

任意健康状态
  -> 人工禁用 -> admin_state=disabled，自动状态不再使其加入路由
```

半开状态同一时间最多放行一个验证请求，防止大量请求同时击穿。冷却时间使用指数退避并设置上限，同时遵守上游 `Retry-After` 中更长的等待要求。`auto_disabled` 是系统状态，不等于人工禁用；只有渠道开启自动恢复且恢复探针连续成功达到阈值时才能自动解除。`auto_recover=false` 时只能由用户手动重置自动状态。人工禁用优先级最高，任何探针结果都不能改变它。健康更新通过带版本号的原子事务串行化，避免真实请求、探针和人工操作同时覆盖状态。

## 9. 主动探针

每个渠道具有独立探针策略：

- 是否启用以及是否允许自动恢复。
- 连通性探针或最小推理探针。
- 探针模型和最小请求正文。
- 周期、随机抖动、连接超时、首字节超时和总时限。
- 连续成功/失败阈值。
- 是否在启动时、冷却结束时执行。
- 探针失败是否延长冷却。

开启 `auto_recover` 时必须同时启用恢复探针；“关闭全部探针但开启自动恢复”属于非法配置，保存和导入时直接拒绝。连续成功阈值必须大于 0。

调度规则：

- 全局限制探针并发数。
- 同一渠道禁止探针重叠执行。
- 定时任务加入随机抖动，避免所有渠道同时请求。
- 人工禁用渠道默认不执行自动探针。
- 手动探针不改变人工状态，但可根据用户选择更新健康状态。
- 探针数据和业务请求数据分开统计。

## 10. SQLite 数据模型

建议的核心表如下，最终字段以迁移脚本为准：

| 表 | 主要职责 |
| --- | --- |
| `schema_migrations` | 数据库版本管理 |
| `settings` | 全局设置和版本化配置 |
| `channels` | 渠道协议、地址、状态、能力和非敏感配置 |
| `channel_secrets` | 只保存密钥引用或加密密文，不进入普通导出 |
| `route_groups` | 协议与逻辑模型对应的路由组 |
| `route_channels` | 路由组中的渠道顺序和优先级 |
| `global_model_mappings` | 协议内客户端模型到逻辑模型的映射 |
| `channel_model_mappings` | 逻辑模型到上游实际模型的映射 |
| `probe_policies` | 渠道探针策略 |
| `channel_health` | 当前健康状态、自动失败动作、连续失败和冷却截止时间 |
| `response_affinities` | Responses ID 与渠道的短期亲和关系 |
| `requests` | 一次逻辑请求的元数据和最终结果 |
| `attempts` | 每次上游渠道尝试和错误分类 |
| `request_contents` | 可选加密正文文件的路径、密钥引用、nonce、哈希、大小、压缩和截断状态 |
| `health_events` | 冷却、半开、恢复和禁用等状态事件 |
| `probe_runs` | 每次探针执行结果 |
| `audit_logs` | 配置变更和数据操作记录 |
| `metric_hourly` | 渠道、协议和模型维度的小时计数、总量和固定延迟直方图桶 |

设计要求：

- `requests` 与 `attempts` 分离，一次逻辑请求经过三个渠道仍然只算一个请求。
- 配置变更使用事务，失败时整体回滚。
- SQLite 开启 WAL、合理的 busy timeout 和定期 checkpoint。
- 聚合表与明细日志保留策略分开，避免清理请求正文后 30 天图表丢失。
- p50/p95 不直接对小时分位数再次求分位数；小时聚合保存固定延迟直方图桶，查询窗口时合并桶后计算近似分位数。
- 正文以本地“先压缩、再分块加密”的内容文件保存，SQLite 只存引用和元数据，避免大型 SSE 正文持续膨胀数据库。

## 11. 日志、隐私和安全

### 11.1 日志级别

支持三档内容策略：

1. `metadata_only`：默认，仅保存模型、渠道、耗时、状态、token 等元数据。
2. `request_content`：额外保存经过已知结构字段和用户自定义规则尽力脱敏的请求内容。
3. `request_and_response_content`：同时保存经过上述规则处理的请求和响应内容。

始终遮盖：

- `Authorization`、`x-api-key`、Cookie 和已知凭证 Header。
- 渠道密钥、管理令牌和代理令牌。
- 导入文件中的敏感字段预览。

脱敏只能保证处理协议中的已知敏感字段和用户配置的规则，不能保证识别 Prompt、工具参数、源码或 Base64 内容中任意形式的秘密，因此内容日志始终属于高风险显式功能。

正文日志具有单条大小上限、全局磁盘配额、保留天数和一键清理能力。每个内容文件使用随机数据密钥；SSE 正文在内存中经过压缩后写入分块 AEAD 加密流，临时文件从第一字节起就是密文，结束后校验并原子改名。数据密钥由平台秘密存储中的主密钥包装，SQLite 只保存密钥引用、nonce、哈希、大小和截断状态。内容目录和临时目录使用当前用户最小文件权限/ACL；程序启动时只清理能够确认属于本应用的孤立加密临时文件。

超限时优先删除最旧正文，再分批删除最旧明细，不能破坏配置和聚合统计。SQLite 日常只执行 WAL checkpoint 和低频 incremental vacuum，不进行会长期阻塞代理的每日完整 vacuum。

日志详情只能以转义后的纯文本或安全 JSON 查看器展示，不把模型返回内容直接作为 HTML 或 Markdown 执行，避免本地管理页出现内容注入或 XSS。

### 11.2 本地鉴权

- 管理令牌与代理令牌分开生成、轮换和撤销。
- 默认禁止跨域访问管理 API。
- 管理 API 校验 `Host` 和 `Origin`，默认只允许明确配置的回环地址；拒绝未知 Host、跨站修改请求和 DNS rebinding 常见入口。
- 管理页面只使用显式管理令牌，不依赖浏览器 Cookie 自动鉴权；写操作仅接受预期的 `Content-Type`，降低 CSRF 风险。
- 管理页面设置严格 CSP，至少限制资源与连接为本地 `self`、禁止被第三方页面嵌入，并且运行时不加载外部 CDN 资源。
- 监听非回环地址时，界面显示明确风险提示并强制启用鉴权。
- 渠道凭证不直接回显，编辑页面只显示掩码和“已配置”状态。
- 导出默认不包含任何密钥；包含密钥的导出必须显式选择并加密。
- 审计日志、运行日志和诊断包永不包含秘密值或正文内容；客户端代理凭证不转发上游，上游凭证不返回下游。

### 11.3 密钥存储

通过秘密存储 Adapter 隔离平台差异：

- Windows 优先使用 DPAPI 或 Credential Manager。
- macOS 使用 Keychain。
- Linux 优先使用 Secret Service。
- 不支持系统密钥环时，进入受限的本地加密模式并明确提示保护边界。

数据库中的渠道记录只引用秘密标识。便携包复制数据库时不会默认带走可直接使用的明文 API Key。

## 12. 统计口径

所有图表都必须明确指标口径：

### 12.1 逻辑请求指标

- 请求总数、最终成功率、最终失败率。
- 端到端总耗时 p50/p95。
- 发生 fallback 的请求数和比例。
- 客户端取消和最终流中断数。

### 12.2 渠道尝试指标

- 渠道实际尝试次数和成功率。
- 首字节/首事件耗时 p50/p95。
- 连接错误、超时、401/403、404、429、5xx 和非法响应次数。
- 同渠道重试次数、冷却次数和自动恢复次数。
- 输入 token、输出 token、缓存读取 token、缓存写入 token。

### 12.3 探针指标

- 探针次数、成功率、延迟和最后成功时间。
- 自动恢复次数与恢复耗时。

当天、7 天和 30 天通过相同聚合口径查询。时间窗口定义为用户时区下的日历窗口：当天从本地 00:00 到当前时间，7 天包含当天及之前 6 个日历日，30 天包含当天及之前 29 个日历日。数据库时间戳和小时桶统一存 UTC，查询时使用 IANA 时区数据库计算本地边界和夏令时，不使用固定 UTC 偏移。

成功和失败口径固定为：

- 逻辑请求“成功”必须收到非流式合法终止响应，或收到对应流式协议的正常终止事件。
- 已提交后断流记为 `partial_failure`，计入失败分母并单独展示，不能记为成功。
- 成功率分母为已通过本地鉴权/校验并进入路由、最终状态为 `success | failure | partial_failure` 的逻辑请求；`client_cancelled` 和本地校验拒绝单独统计，不进入成功率分母。
- 渠道 Attempt 只有在协议正常终止时才算成功；仅收到首事件不算成功。
- fallback 请求比例 = 使用两个及以上不同渠道的逻辑请求数 / 至少启动过一个 Attempt 的非客户端取消逻辑请求数。
- 探针不进入业务请求和 Attempt 成功率。

缓存不强行归并为一个可能误导的“命中率”：

- 优先展示缓存读取 token / 总输入 token。
- 同时展示返回缓存字段的请求覆盖率。
- 上游没有提供缓存字段时显示“未知”，不能当作 0 或未命中。

跨请求缓存 token 比例按 `sum(cache_read_input_tokens) / sum(input_tokens)` 加权计算，不能平均每条请求的比例。延迟桶初始边界为 `[25, 50, 100, 250, 500, 1000, 2000, 5000, 10000, 30000, 60000, +Inf]ms`，端到端延迟和首事件延迟分别聚合；p50/p95 显示为近似值，允许误差不超过命中桶宽度，进入 `+Inf` 桶时只显示“超过 60s”而不伪造精确值。

## 13. 配置与数据管理

### 13.1 配置热更新

可热更新：

- 渠道启用状态、优先级和能力声明。
- 路由组和两级模型映射。
- 重试、fallback、冷却和探针参数。
- 日志内容策略、保留期和磁盘配额。
- 主题和大部分管理页面设置。

需要重启：

- 代理监听地址和端口。
- 管理监听地址和端口。
- 数据目录和密钥存储初始化方式。

设置保存前应校验端口冲突，并清楚显示“立即生效”或“重启后生效”。

### 13.2 导入导出格式

项目自定义 JSON 格式必须带 Schema 版本：

```json
{
  "schemaVersion": 1,
  "exportedAt": "2026-08-27T00:00:00Z",
  "appVersion": "0.1.0",
  "channels": [],
  "routeGroups": [],
  "globalModelMappings": [],
  "channelModelMappings": [],
  "probePolicies": [],
  "settings": {}
}
```

导入流程固定为：文件解析 -> Schema 校验 -> 语义校验 -> 冲突检测 -> 差异预览 -> 自动备份 -> 单事务写入 -> 失败回滚。需要检测重复 ID、未知协议、缺失渠道、模型映射环和无候选路由组。

配置导出与完整备份是两个不同概念：

- 配置导出只包含渠道、路由、模型映射、探针策略和通用设置；默认不包含密钥、请求正文、明细日志、健康运行态和 Responses 亲和记录。
- 完整备份包含一致性 SQLite 快照、仍在保留期内的加密正文文件和备份清单；过期亲和记录在恢复后清理。
- 完整备份不写入平台主密钥明文。同一系统用户恢复时复用系统密钥环；跨设备迁移秘密必须走用户显式启用、带口令加密的秘密导出流程。
- 升级前备份与导入前备份均使用完整备份语义，恢复时先校验数据库、内容文件清单和版本兼容性，再原子切换。

## 14. 前端信息架构

管理页采用顶部主导航，不使用常见的深蓝色固定侧边栏。主页面包括：

1. **概览**：服务状态、今日关键指标、渠道健康摘要、最近故障。
2. **渠道**：渠道列表、创建/编辑、试连、人工启停、优先级和能力。

5. **请求日志**：筛选、请求列表、Attempt 链路、请求/响应内容和错误详情。
6. **统计分析**：当天、7 天、30 天，按协议、渠道和模型切换维度。
7. **设置**：监听、超时、重试、冷却、日志、鉴权、主题和数据目录。
8. **数据管理**：导入、导出、备份、清理和诊断信息。

- 功能状态色使用低饱和绿、黄、红，并配合文字或图标，不能只用颜色表达。
- `#87867F`、`#B0AEA5`、`#D97757`、`#C6613F` 不用于浅色背景上的普通小字号正文；正文使用 `#141413`、`#5E5D59` 或可访问暖色 `#8A3F2A`。
- 图表使用暖黑、暖灰、米色和少量低饱和强调色，禁止彩虹配色、蓝紫渐变和玻璃拟态。
- 图标统一使用自有 SVG 或同一开源线性图标集，不使用 emoji 作为功能图标。

### 15.5 暗色主题

Anthropic 官网当前不是随系统自动切换整站暗色，本项目暗色主题属于基于其深色区块的扩展：

| 语义 | 暗色值 |
| --- | --- |
| 页面背景 | `#141413` |
| 表面背景 | `#232321` |
| 悬停表面 | `#3D3D3A` |
| 主文字 | `#FAF9F5` |
| 次文字 | `#B0AEA5` |
| 分隔线 | `rgba(250,249,245,.16)` |

主题通过统一 CSS 变量切换，不为各页面重复定义色值。暗色仍然使用暖黑，不使用纯黑、蓝黑和霓虹色。

### 15.6 布局、响应式和动效

- 所有布局使用 flex、宽度、margin 和 padding；禁止 CSS `grid` 和 `gap`。
- 检查 375px、768px、1024px 和 1440px 四个宽度。
- 宽屏展示完整顶栏和横向卡片；窄屏折叠导航，卡片单列排列。
- hover 和状态变化为 150～200ms；抽屉和弹层为 200～300ms。
- 不照搬营销页的大段入场动画，不允许持续闪烁健康状态。
- 必须支持 `prefers-reduced-motion`、键盘导航、可见焦点和 WCAG AA 对比度。

### 15.7 视觉一致性验收

“Anthropic 风格”是所有管理页面的统一硬约束，不允许只在登录页、概览页或空状态中局部使用。实施和评审按以下清单核对：

- 页面壳固定使用暖色背景、约 1432px 内容上限、68px 顶栏和克制的横向导航，不套用深色侧边栏后台模板。
- 标题、编辑说明和技术数据分别使用 sans、serif、mono 三种排版角色；字号层级、行高、段落宽度和上下留白形成编辑出版感。
- 按钮、表单、卡片、表格、抽屉、状态标识、图表和代码查看器全部来自同一组设计令牌，不保留第三方组件库默认皮肤。
- 浅色主题精确使用本章冻结的核心色值、圆角和分隔线关系；任何偏离必须在设计令牌变更记录中说明原因。
- 暗色主题保持同样的暖黑、象牙白和低饱和层级，不转换成常见蓝黑运维大屏风格。
- 概览、渠道、路由、探针、日志、统计、设置和数据管理都要覆盖正常、空、加载、错误、禁用和危险确认状态。
- 在 1440px、1024px、768px、375px 下保存项目自有基线截图并逐页复核视觉与交互；基线用于保证风格一致，不复制 Anthropic 官网具体构图、品牌内容或源码。

## 16. 技术选型与目录规划

### 16.1 后端

- Go 标准库 HTTP 能力为主，避免引入大型 Web 框架。
- `log/slog` 输出结构化运行日志。
- 采用纯 Go SQLite Driver，避免 CGO 带来的跨平台构建负担。
- SQL 迁移文件内嵌到二进制，启动时按版本顺序执行。
- 使用有界 HTTP Transport、连接池和 Context 取消传播。

### 16.2 前端

- Vue 3、TypeScript、Vite、Vue Router、Pinia。
- 自建轻量组件和设计令牌，不套用通用后台 UI 组件库的默认皮肤。
- 图表使用可按需引入的 ECharts 模块。
- 使用 CSS 自定义属性管理浅暗主题，普通 CSS 或 scoped CSS 实现布局。
- 静态资源全部随发布包提供，管理页面运行时不依赖外部 CDN。

### 16.3 建议目录

```text

    responses/

  internal/routing/            # 模型映射、路由计划和模拟

  internal/health/             # 健康状态机
  internal/probe/              # 探针调度和执行

  internal/secrets/            # 平台密钥存储 Adapter

  internal/webui/              # 嵌入的 Vue 构建产物
```

### 16.4 实现约束

- 每个文件控制在约 1000 行以内，超过时按职责拆分，不建立无实际变化点的抽象层。
- 前端每个方法定义上方添加规范中文注释；Go 导出声明使用符合 Go Doc 规则的中文注释。Go 不使用 Java Javadoc 语法。
- 不顺手重构与当前阶段无关的代码，不提前实现后续版本能力。
- 前端样式禁止使用 CSS `grid` 和 `gap`，不引入会强制产生这些属性且无法覆盖的布局组件。
- 不主动提交代码；每个阶段完成后只报告变更、验证结果和未验证边界。

## 17. 分阶段实施计划

### 阶段 0：规格冻结与反馈环

**工作内容**

- 固化协议枚举、领域术语、错误分类、状态迁移和统计口径。
- 确定默认端口、数据目录、配置 Schema 和导出 Schema。
- 准备三个协议的最小成功、错误和 SSE 样例，以及可控的本地假上游。
- 重新采集 Anthropic 官网桌面/移动视觉基线和计算样式。
- 冻结自有页面线框、可访问语义色和开源字体许可证清单，官网 CSS 仅作为测量证据。

**交付物**

- 领域模型说明、错误策略矩阵、状态机表和验收场景清单。
- 临时假上游与可复跑验证命令；验证完成后不将测试文件保留在项目中。

**验收**

- 每项 V1 功能都能映射到至少一个可执行验收场景。
- 协议、请求、Attempt、渠道失败和探针的统计口径没有歧义。

### 阶段 1：工程骨架与本地启动

**工作内容**

- 初始化 Go 和 Vue 工程，建立依赖组装、优雅关闭和结构化日志。
- 建立 SQLite 连接、迁移、WAL 和备份机制。
- 实现代理监听器、管理监听器、`/healthz` 和嵌入式静态页面。
- 建立配置读取、校验和“需要重启”标记。

**验收**

- 单个发布目录可以启动服务、创建数据库并访问管理页。
- 修改热更新配置立即生效；修改监听设置明确提示重启。

### 阶段 2：渠道、路由和模型配置

**工作内容**

- 实现渠道、路由组、能力声明和两级模型映射的数据模型与管理接口。
- 实现优先级排序、候选过滤、配置校验和路由模拟。
- 实现管理令牌与代理令牌。

**验收**

- 同一厂商可以建立三个协议渠道；协议不一致的渠道关系无法保存、无法导入，也不会参与路由。
- 同优先级候选始终按照 `(priority, position, channel_id)` 稳定排序，相同输入重复模拟和执行都得到同一渠道顺序。
- 路由模拟能显示映射、顺序、跳过原因和无候选错误。

### 阶段 3：三种协议转发

按 `OpenAI Responses -> Anthropic Messages -> OpenAI Chat` 的顺序实现，每次只完成一个协议的非流式、流式、错误解析和 usage 解析，再进入下一个协议。

**验收**

- 每种协议的 JSON 请求、SSE 请求、工具调用字段和自定义 Header 均原样兼容。
- 客户端取消能停止上游请求。
- Codex 使用 Responses 入口和 Claude Code 使用 Messages 入口完成真实最小请求。

### 阶段 4：重试、fallback 与健康状态机

**工作内容**

- 实现 Attempt 账本、时间/次数预算、错误分类和策略表。
- 实现同渠道重试、按优先级 fallback、连续失败计数、指数冷却和系统自动禁用策略。
- 实现 half-open 单请求放行、人工禁用隔离和 Responses 亲和。
- 实现流式提交点，禁止提交后切换渠道。

**验收**

- 可控假上游能复现 A 重试耗尽后依次切换 B、C。
- 连续失败达到阈值后，后续请求跳过冷却渠道。
- 选择自动禁用策略的渠道达到阈值后进入 `auto_disabled`，只有符合配置的恢复探针或人工重置才能恢复。
- OpenAI Chat 以首个合法、非注释、非 `[DONE]` 的 JSON `data` 帧为提交点；OpenAI Responses 以兼容矩阵冻结的首个合法生命周期事件为提交点；Anthropic Messages 以合法 `message_start` 为提交点。
- 各协议提交点前失败可以按预算重试或切换，提交点后断开只记录流中断，不拼接其他渠道。
- 人工禁用不会被真实请求或探针自动恢复。

### 阶段 5：探针与自动恢复

**工作内容**

- 实现探针策略、调度、抖动、并发限制和手动执行。
- 实现冷却到期进入 half-open、探针成功恢复、失败延长冷却。
- 区分探针统计和业务统计。

**验收**

- 指定渠道可以单独开关探针。
- `auto_recover=true` 时恢复探针必须启用，未启用的配置不能保存或导入。
- 冷却或系统自动禁用渠道只有在恢复探针连续成功达到配置阈值后，才自动恢复并重新参与优先级路由。
- `auto_recover=false` 的渠道只能由用户手动重置自动健康状态。
- 人工禁用渠道保持禁用，任何自动或手动探针都不能解除人工禁用。

### 阶段 6：日志、统计与清理

**工作内容**

- 实现 requests、attempts、health_events、probe_runs 和 audit_logs。
- 实现元数据/正文日志策略、脱敏、大小限制和磁盘配额。
- 实现小时聚合以及当天、7 天、30 天查询。
- 实现按保留天数、磁盘配额和手动操作清理。

**验收**

- 一条请求可以查看所有渠道尝试、重试次数和最终原因。
- 关闭正文记录后数据库不保存 Prompt 和响应正文。
- 开启正文记录后，正文文件从第一字节起以“压缩后分块 AEAD 加密”形式写入，数据库只保存密钥引用和校验元数据；异常退出不会留下明文临时文件。
- 清理明细日志后，保留期内聚合统计仍然可查询。
- 未知缓存数据在页面显示“未知”。
- 当天、7 天、30 天严格使用用户时区下的日历窗口；成功率、fallback 比例和缓存比例使用第 12 章定义的固定分母。

### 阶段 7：Anthropic 风格管理页面

**工作内容**

- 先建立设计令牌、排版、顶栏、按钮、表单、卡片、表格、抽屉和代码查看器。
- 再按概览、渠道、路由与模型、探针、日志、统计、设置、数据管理顺序实现页面。
- 实现浅色、暗色、跟随系统和主题持久化。
- 实现错误、空状态、加载状态和危险操作确认。

**验收**

- 与冻结后的项目设计令牌和自有线框在色彩关系、排版角色、留白、圆角和分隔线方面一致，不复制官网具体页面构图。
- 概览、渠道、路由、探针、日志、统计、设置和数据管理的全部状态均通过第 15.7 节视觉一致性清单，不出现通用后台模板或第三方组件默认皮肤。
- 全部页面不使用 CSS `grid` 和 `gap`。
- 375px、768px、1024px、1440px 无横向溢出，主要流程可操作。
- 浅暗主题均达到可读对比度，键盘焦点可见，减少动效设置生效。

### 阶段 8：导入导出、安全和恢复

**工作内容**

- 实现 Schema 校验、差异预览、冲突处理、自动备份和事务导入。
- 接入三平台秘密存储 Adapter。
- 实现令牌轮换、数据库备份恢复和诊断信息导出。

**验收**

- 配置导出再导入后，渠道、路由、映射和探针策略保持一致。
- 默认导出不包含密钥。
- 非法导入不会产生部分写入，失败后原配置不变。
- 完整备份能校验并恢复 SQLite、加密正文和清单；配置导出不会意外携带正文、运行态或 Responses 亲和记录。

### 阶段 9：跨平台发布与真实客户端验收

**工作内容**

- CI 构建 Windows、macOS、Linux 的 amd64/arm64 目标。
- V1 先提供便携压缩包；后续增加 Windows 安装程序、macOS App/DMG、Linux AppImage/deb。
- 验证升级保留数据库与配置，升级前自动备份。
- 编写 Codex 和 Claude Code 的本地接入说明。
- 实现单实例锁、端口冲突提示、前台停止和升级时活动请求/数据库锁处理。
- 为每个产物标注正式或实验支持状态，正式 Windows/macOS 产物完成签名与公证。

**验收**

- 全新机器无需 Go 或 Node.js 即可启动。
- 每个标记为正式支持的 OS/架构产物均完成启动、首次初始化、管理页访问、端口冲突、单实例和优雅退出 smoke test；未完成者只能标记实验支持。
- Codex Responses 与 Claude Code Messages 完成真实端到端请求和一次故障切换验证。

## 18. 验证策略

遵循“验收条件先行 -> 最小实现 -> 定向验证 -> 按风险补临时测试”。项目约束要求测试文件不保留，因此：

- 每个高风险核心行为先建立临时 Go/Vitest 测试或假上游反馈环。
- 修复或实现后复跑同一反馈环。
- 测试通过后删除临时测试文件，不把它们纳入最终项目。
- Go 侧执行格式化、静态检查和针对性竞争检查。
- Vue 侧执行类型检查和正式构建。
- 页面使用可复跑浏览器流程验证功能；视觉验收另外对比 Anthropic 基线。
- 构建通过不等同于 Codex、Claude Code 或三平台真实运行通过，交付时分别说明验证边界。

## 19. V1 总体验收标准

- [ ] 三个协议入口互相隔离且均支持非流式和 SSE。
- [ ] 每个渠道只能选择一种协议，路由不会跨协议混用。
- [ ] 跨协议渠道关系不能保存或导入，也不能参与路由。
- [ ] 两级模型映射按预期生效；候选渠道按照 `(priority, position, channel_id)` 确定性排序。
- [ ] 同渠道重试耗尽后按优先级逐一 fallback，并受总预算约束。
- [ ] 连续失败达到阈值后按渠道策略进入冷却或系统自动禁用；`auto_recover=true` 仅在恢复探针连续成功达标后自动恢复，`auto_recover=false` 只能人工重置。
- [ ] 人工禁用不会被自动恢复。
- [ ] Chat、Responses、Messages 分别按协议级提交点判定；提交前可 fallback，提交后不拼接其他渠道。
- [ ] Responses `previous_response_id` 保持渠道亲和。
- [ ] 每条逻辑请求能查看完整 Attempt 链路和可解释错误。
- [ ] 日志正文默认关闭；开启后执行密钥遮盖、限额、清理，并以压缩后分块 AEAD 加密文件保存。
- [ ] 当天、7 天、30 天使用用户时区日历窗口，指标能区分逻辑请求、渠道尝试和探针，且成功率、fallback、缓存比例分母符合第 12 章。
- [ ] 缓存未知值不会误显示为 0 或未命中。
- [ ] 配置导入前有校验和差异预览，失败能完整回滚。
- [ ] 浅暗主题、响应式和无障碍检查通过，页面不使用 `grid` 与 `gap`。
- [ ] 前端符合 Anthropic 高保真视觉语言且不复制其受保护品牌素材。
- [ ] 普通用户在 Windows、macOS、Linux 上无需 Go/Node.js 即可运行发布包。
- [ ] 每个标记为正式支持的 OS/架构都完成阶段 9 定义的 smoke test；未验证产物只能标记实验支持。

## 20. 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| SSE 已输出后错误切换造成内容拼接或重复计费 | 高 | 明确提交点，提交后禁止 retry/fallback |
| Responses ID 在不同渠道不兼容 | 高 | 持久化短期渠道亲和，默认不跨渠道切换 |
| 重试扩大延迟和费用 | 高 | 次数、渠道数和总时限三重预算，记录重试原因 |
| 401/404 等错误策略不合理导致反复请求 | 中 | 结构化错误策略矩阵，可配置且有保守默认值 |
| 完整日志泄露 Prompt、源码或密钥 | 高 | 元数据默认、显式开启、脱敏、限额、加密和一键清理 |
| SQLite 明细增长过快 | 中 | 内容分表、小时聚合、保留期、磁盘配额和 WAL 维护 |
| 探针本身产生费用或误判 | 中 | 两种探针模式、独立阈值、并发限制和独立统计 |
| 三平台密钥环行为不同 | 中 | 秘密存储 Adapter、明确降级提示和平台验收 |
| 官网风格随时间变化 | 低 | 实施前采集基线，随后以项目设计令牌为稳定标准 |
| “完全复制”造成品牌或版权风险 | 中 | 复现视觉语言，自建品牌、字体替代、素材和组件实现 |
| macOS/Windows 未签名包产生警告 | 中 | 未签名产物只能作为测试构建；正式公开分发必须完成 Windows Authenticode、macOS 签名/公证和校验和发布 |
