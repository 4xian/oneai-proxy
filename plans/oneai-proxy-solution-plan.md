## 1. 目标与决策摘要

OneAI Proxy 是一个面向单机用户的本地 AI 请求代理。它在 Codex、Claude Code 或其他兼容客户端与多个上游厂商之间提供稳定的协议转发、按优先级容灾、自动恢复、日志审计和统计分析能力。

已确定的核心决策如下：

1. 后端使用 Go，前端使用 React 19 + TypeScript，数据使用 SQLite。
2. V1 采用本地服务页面，不以 Tauri、Wails 或 Electron 作为核心运行方式。
3. React 构建产物嵌入 Go 可执行文件。普通用户安装或运行发布包时不需要 Go、Node.js 或 npm。
4. 支持三个独立协议入口，但不做跨协议转换：
   - OpenAI Chat Completions：`POST /v1/chat/completions`
   - OpenAI Responses：`POST /v1/responses`
   - Anthropic Messages：`POST /v1/messages`
5. 每个渠道只能属于一种协议。同一厂商如果支持多个协议，应配置为多个独立渠道。
6. 同协议渠道按渠道自身优先级从高到低依次尝试；同一逻辑请求对每个渠道最多发起一次实际上游调用，失败后立即切换下一个可准入渠道，不做同渠道自动重试。
7. 连续失败阈值决定渠道何时进入冷却或系统自动禁用，不决定当前请求何时切换渠道。
8. 人工禁用、系统自动冷却和系统自动禁用必须分开；人工禁用的渠道不能被探针自动恢复。
9. 请求日志默认保存加密的请求/响应快照；管理 API 对 API 凭证脱敏，Cookie 在管理页面可显示原值。运行日志单独写入本地文件并以 `***` 替换敏感凭证。
10. 前端统一采用本计划第 15 章的 Apple 风格规范，使用本项目自己的名称、图标、组件、文案和实现代码，不复制 Apple 的商标、专属字体文件、图片、视频或源码。

需要保留的官方兼容性边界：当前 Codex 官方自定义 Provider 配置中，`wire_api` 只明确支持 `responses`。因此本代理会提供 Chat 和 Responses 两种 OpenAI 协议，但 Codex CLI 的正式接入以 Responses 为基线；Chat 入口主要面向 OpenAI Chat 客户端、SDK 和其他兼容客户端。

三个 `POST` 入口是已确认的核心范围。阶段 3 在代理实现后捕获当前 Codex 和 Claude Code 的真实调用清单；如果客户端确实调用 Responses 资源查询/取消接口或 Messages `count_tokens` 等伴随接口，应按原协议补入 V1，并让资源 ID 延续原渠道亲和，不能把伴随请求随机发送给其他渠道。

## 2. 产品范围

### 2.1 V1 范围

- 三种协议的非流式和 SSE 流式转发。
- 渠道、优先级、兜底模型和能力声明管理。
- 访问组与渠道 M:N、列表代理密钥单组绑定，以及独立管理员通用代理令牌。
- 列表密钥和渠道的微美元额度、Attempt 级精确计费与幂等结算。
- 全局与可承接渠道的规范化敏感词拦截。
- 全局模型映射和渠道级模型映射。
- 跨渠道模型资料目录：在线源预览同步、手工新增、费用参考、来源状态和渠道编辑联想。
- 跨渠道失败重试、非阻塞并发准入、连续失败阈值、冷却、半开和自动恢复。
- 主动探针、手动探针、启动探针和冷却结束探针。
- 请求日志、渠道尝试日志、健康事件、探针记录和配置审计记录。
- 当天、7 天、30 天统计以及渠道级延迟、成功率、缓存相关指标。
- 监听地址、端口、超时、重试、冷却、日志等通用设置。
- 渠道和相关配置的导入、导出、校验、差异预览和回滚。
- 浅色、暗色和跟随系统主题。
- Windows、macOS、Linux 的可运行发布包。

### 2.2 V1 不做

- Chat、Responses 和 Messages 之间的相互转换。
- OAuth 账号池、多账号轮询、计费售卖、充值和多用户配额分发；阶段 13 的单机列表密钥/渠道固定额度不属于商业配额系统。
- 多用户、组织、角色权限和远程公网管理。
- 任意 JavaScript/Lua 脚本改写请求。
- 基于权重、成本或实时延迟的智能负载均衡；V1 只按显式优先级顺序尝试。
- 桌面托盘、原生通知和强依赖桌面壳的功能。
- 直接复制其他代理项目的代码组织、数据库结构或实现。

### 2.3 后续版本候选

- 面向客户端的 `/v1/models` 聚合接口；管理台模型目录不等同于该代理接口。
- 渠道能力自动检测与模型级健康状态。
- Responses WebSocket 传输。
- 费用估算和价格表管理。
- 系统托盘、开机启动、原生通知和一键打开管理页。
- 诊断包导出、日志全文检索和更完整的失败原因分析。

## 3. 用户安装与使用方式

### 3.1 开发环境与用户环境

| 场景             | Go     | Node.js | 说明                                 |
| ---------------- | ------ | ------- | ------------------------------------ |
| 本地开发         | 需要   | 需要    | Go 编译后端，Node.js 构建 React 页面 |
| CI 发布          | 需要   | 需要    | 构建三平台产物并完成打包             |
| 普通用户安装使用 | 不需要 | 不需要  | 运行已经编译并嵌入前端资源的发布包   |

### 3.2 用户首次使用流程

1. 用户下载对应系统和 CPU 架构的发布包。
2. 首次启动时创建数据目录、SQLite 数据库、配置文件和本地默认凭证（管理令牌 `oneai-local-admin`、代理令牌 `sk-oneai-admin-proxy`）。阶段 13 不识别旧代理默认值。
3. 服务默认只监听 `127.0.0.1`，不暴露到局域网。
4. 用户打开本地管理页，添加渠道并选择协议。
5. 用户配置渠道实际模型、逻辑模型、渠道优先级、重试、冷却和探针。
6. 用户执行“试连”或手动探针，确认渠道可用。
7. 用户将 Codex 或 Claude Code 的 Provider 地址指向本地代理。
8. 后续请求由 OneAI Proxy 自动执行重试、fallback、冷却和恢复。

### 3.3 数据目录

默认使用操作系统约定的数据目录：

- Windows：`%LOCALAPPDATA%\OneAI Proxy\`
- macOS：`~/Library/Application Support/OneAI Proxy/`
- Linux：`$XDG_DATA_HOME/oneai-proxy/`，未设置时使用 `~/.local/share/oneai-proxy/`

目录内至少包含数据库、配置、备份和可选内容日志。命令行参数 `--data-dir` 用于便携模式和故障恢复。

### 3.4 V1 便携包运行闭环

- Windows 解压后运行 `oneai-proxy.exe serve`；macOS/Linux 解压后运行 `./oneai-proxy serve`。
- 便携版默认前台常驻，在控制台输出代理地址、管理地址、数据目录和停止方式；用户在浏览器手动打开管理地址，按 `Ctrl+C` 触发优雅停止。
- 同一数据目录通过进程锁保证单实例。第二个实例发现锁后输出已有实例信息并退出，不能并发打开同一 SQLite 数据库。
- 端口占用时明确报告冲突地址并退出，不静默改用随机端口。
- 便携版崩溃后不承诺自动重启；用户级服务、自启动和崩溃拉起由后续原生安装包提供。
- Windows 说明前台控制台窗口不可关闭；Linux 包保留执行权限并提供 `chmod +x` 故障提示；macOS 正式包必须完成签名和公证，否则只能标记为测试构建并说明 Gatekeeper 操作边界。
- 升级前停止接收新请求，等待活动请求或达到优雅退出时限，释放数据库锁并自动备份后再替换二进制。迁移失败时恢复数据库备份并保留旧版本可执行文件。
- CI 可以构建六个 OS/架构目标，但只有完成对应目标真实或等价硬件 smoke test 的产物才能标记“正式支持”，其余必须标记“实验支持”。正式公开分发要求 Windows Authenticode 签名、macOS 签名/公证以及全部产物 SHA-256 校验和。

## 4. 总体架构

```text
Codex / OpenAI-compatible clients / Claude Code
                         |
              Local proxy listener
                         |
              Protocol entry adapters
       +-----------------+-----------------+
       |                 |                 |
 OpenAI Chat       OpenAI Responses   Anthropic Messages
       |                 |                 |
       +--------- Request envelope --------+
                         |
             Model mapping + route plan
                         |
      Capability filter + priority ordering
                         |
      Retry / fallback / request time budget
                         |
         Channel health state + affinity
                         |
              Upstream protocol channel
                         |
         Request/attempt/probe event records
                         |
       SQLite + aggregation + log retention
                         |
               Admin API + React 19 UI
```

建议一个进程内提供两个监听器：

- 代理监听器：只承载 `/v1/*` 客户端请求。
- 管理监听器：承载管理页面、`/api/admin/v1/*` 和 `/healthz`。

两个监听地址和端口均可配置，默认都只绑定回环地址。代理令牌与管理令牌分离。这样即使未来用户主动将代理监听器开放到局域网，也不必同时暴露管理页面。

## 5. 领域模型与术语

| 术语                             | 定义                                                                                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 协议 `Protocol`                  | `openai_chat`、`openai_responses`、`anthropic_messages` 之一                                                                         |
| 厂商 `Provider`                  | OpenAI、Anthropic、Azure 或第三方兼容服务，仅用于分类和展示                                                                          |
| 渠道 `Channel`                   | 一个确定的协议、上游地址、凭证、连接设置和能力声明                                                                                   |
| 能力声明 `Capability`            | 渠道对请求特征的可选承接条件，例如流式、工具调用、视觉、音频或推理；为空表示不限制。模型目录中的能力只用于展示和筛选，不限制代理请求 |
| 模型目录记录 `ModelCatalogEntry` | 用于展示、搜索、费用参考和渠道编辑联想的标准化模型资料，不是代理白名单                                                               |
| 模型来源 `ModelSource`           | 一个公开 JSON 地址及其适配器、版本和同步状态                                                                                         |
| 模型来源状态                     | `valid`、`retired` 或 `protocol_unconfirmed`                                                                                         |
| 逻辑模型 `LogicalModel`          | 本地用于稳定路由的模型别名                                                                                                           |
| 全局模型映射                     | 两个协议族各自维护的 `客户端模型 -> 逻辑模型` 单层映射；OpenAI 编辑区同时覆盖 Chat 与 Responses，Anthropic 编辑区覆盖 Messages       |
| 渠道级模型映射                   | `(渠道, 逻辑模型) -> 上游实际模型`                                                                                                   |
| 逻辑请求 `Request`               | 客户端发起的一次请求，不因重试或 fallback 增加数量                                                                                   |
| 渠道尝试 `Attempt`               | 逻辑请求在某个渠道上的一次实际上游调用                                                                                               |
| 探针 `Probe`                     | 独立于真实业务请求的渠道可用性检查                                                                                                   |
| 健康状态                         | 系统根据真实请求和探针结果维护的自动状态                                                                                             |
| 人工状态                         | 用户显式启用或禁用渠道的管理状态                                                                                                     |
| 自动失败动作                     | 渠道达到连续失败阈值后进入 `cooldown` 或 `auto_disabled` 的策略                                                                      |

渠道编辑中的 Base URL 填写上游 API 根地址，可以保留上游要求的 `/v1` 路径；协议适配器会规范化路径并避免重复拼接。客户端访问本地代理时才使用本地监听器的 `/v1` 地址，不能把本地代理地址填入渠道。

模型解析顺序固定为：

```text
客户端请求 model
  -> 按协议筛选渠道
  -> 按渠道 priority 降序得到候选
  -> 优先匹配客户端 model 的渠道映射
  -> 未命中时匹配渠道模型目录中的同名模型
  -> 未命中时匹配全局映射后的渠道映射
  -> 未命中时匹配渠道模型目录中的全局映射模型
  -> 仍未命中时使用该渠道 fallbackModel
  -> 上游实际 model
```

全局映射按协议族存储，不把 Chat、Responses、Messages 写进 JSON 条目：`openai_chat` 与 `openai_responses` 读取 `openai` 编辑区，`anthropic_messages` 读取 `anthropic` 编辑区。它只把客户端模型名转换为逻辑模型名；路由随后仍按请求协议筛选渠道，因此不会把一个协议的请求发送到另一协议渠道。渠道级映射继续包含精确协议并必须与渠道协议一致。

## 6. 核心模块与接口接缝

采用“接口小、实现深”的模块设计。调用方只感知少量稳定接口，协议差异、重试细节、状态转换和存储实现保留在模块内部。

### 6.1 协议适配模块

三个 Adapter 分别负责：

- 识别 `model`、`stream` 和必要能力。
- 保留对应协议的原始 JSON 和 SSE 事件语义。
- 注入认证 Header、自定义 Header、query 参数和路径前缀。
- 只执行允许的同协议改写，例如模型名替换和固定字段覆盖。
- 解析上游错误、usage、缓存 token 和响应 ID。
- 判断流式响应何时进入“已提交”状态。
- 清除 hop-by-hop Header，且不把本地代理鉴权 Header 发送给上游。
- 不修改用户输入、system prompt、工具定义和多模态正文。

对渠道执行模块暴露的核心接口概念为：

```text
Prepare(inbound request, channel target) -> prepared attempt
Execute(context, prepared attempt, event sink) -> attempt result
Probe(context, channel, probe policy) -> probe result
```

不会把 Chat、Responses 和 Messages 强行转换成一个统一的厂商请求对象。共享的是执行策略和观测事件，不是协议正文。

### 6.2 渠道候选规划模块

输入协议、客户端模型、请求能力和可选亲和信息，输出有序候选列表。其内部完成：

1. 按请求协议筛选渠道。
2. 记录人工状态与健康状态快照；真正发送前仍由运行时准入模块重新检查，不能把候选生成时的快照当作最终准入结果。
3. 标记 `cooldown`、`half_open`、`auto_disabled` 等运行态及其跳过原因；到期冷却能保留为候选并在准入时原子进入 `half_open`。
4. 渠道能力过滤；渠道未声明任何能力时视为不限制，显式声明能力时才要求请求能力全部命中。
5. Responses 亲和渠道约束。
6. 按 `(priority DESC, created_at ASC, channel_id ASC)` 进行稳定排序。
7. 先查客户端原始模型的渠道映射，再查全局映射后的渠道映射。
8. 两级映射均未命中时使用当前渠道的兜底模型；没有兜底模型则跳过当前渠道。

独立“渠道候选模拟”入口与 `routes/simulate` 已删除。真实代理请求仍按上述规则生成候选并记录跳过原因；不再提供单独的模拟页。

数据库约束、管理接口和导入校验都必须保证渠道映射协议与渠道协议一致，全局映射只在自身协议内生效。相同 `priority` 允许存在，由渠道 `created_at` 和 `channel_id` 形成稳定的第二、第三排序，保证任何一次执行都按同一 A、B、C 顺序尝试。

### 6.3 容灾执行模块

容灾执行模块接收渠道候选计划并隐藏准入、切换和状态转换细节，对外只返回最终结果和完整尝试账本。每个候选在真正发送前调用非阻塞 `TryAcquire`：人工禁用、不可路由健康状态、已被其他半开验证领取或渠道并发已满时立即返回结构化跳过原因，不等待当前渠道释放名额。成功准入返回唯一 lease；实际调用结束、客户端取消、账本失败或 panic 路径都必须幂等释放。

关键预算只保留：

- 单请求最大实际渠道尝试数；`0` 表示遍历全部合格候选，跳过候选不消耗次数。
- 连接超时、首字节超时、流空闲超时和逻辑请求总超时。
- 每个渠道独立的硬并发上限；业务请求与真正发往上游的探针共用该上限。

不再提供同渠道自动重试或客户端排队等待配置。所有循环受唯一渠道集合和总时间预算约束，避免无限重试、请求放大和重复计费。

策略取值顺序固定为“系统内置默认值 -> 全局请求配置 -> 渠道配置”。全局配置控制逻辑请求总预算，渠道配置控制优先级、并发、单次调用超时、连续失败阈值、互斥失败动作、冷却基数和恢复策略。独立候选模拟入口已删除，最终生效值由真实请求的路由事件和 Attempt 记录体现。

### 6.4 健康状态模块

健康状态与并发准入收敛为一个深模块。调用方只使用 `TryAcquire(candidate, purpose)`、lease 的 `Finish(outcome)` 和人工 `Reset(channel)`；模块内部负责实时状态检查、并发占位、半开唯一领取、版本校验、失败计数、冷却/自动禁用转换及释放。调用方不得直接修改计数、状态、冷却时间或进程内在途数。

### 6.5 观测与存储模块

请求执行只发送结构化事件，不直接拼装统计 SQL。存储模块负责事务落库，聚合模块负责把原始事件汇总为小时桶和时间窗口指标。这样可以在清理正文或明细日志后继续保留 30 天统计。

## 7. 请求生命周期

### 7.1 普通请求

```text
鉴权和大小检查
  -> 协议识别与浅解析
  -> 按协议和渠道优先级生成候选
  -> 从最高优先级候选开始逐个非阻塞准入
  -> 渠道映射优先解析模型，未命中则使用全局映射，最后使用渠道兜底模型
  -> 满载、冷却、自动禁用或半开名额已占用：记录原因并跳过
  -> 准入成功：当前渠道只执行一次实际上游调用
  -> 成功：记录结果并结束
  -> 失败：原子记录 Attempt 和一次渠道连续失败，立即释放并发名额
  -> 未达到总预算：切换下一个渠道
  -> 全部失败：返回最后一个可解释错误和 request_id
```

### 7.2 流式请求

流式切换遵守一条不可破坏的规则：

- 向客户端输出第一个有效协议正文事件之前，可以切换到尚未尝试的下一渠道。
- 输出有效正文事件之后，不再切换渠道，不拼接另一个上游的响应。

实现时需要区分“收到上游 HTTP Header”和“向客户端提交有效正文”。三种协议的提交点在阶段 0 固化成 Adapter 规则表，初始基线为：

| 协议               | 触发提交的首个事件                                                                                              |
| ------------------ | --------------------------------------------------------------------------------------------------------------- |
| OpenAI Chat        | 第一个完整、合法、非注释、非 `[DONE]` 的 `data` JSON 帧                                                         |
| OpenAI Responses   | 第一个符合当前官方 Responses 事件样例的合法生命周期事件；具体允许事件名随本计划协议基线和使用说明兼容性快照维护 |
| Anthropic Messages | 合法的 `message_start` 事件                                                                                     |

SSE 注释、空帧、ping 和 keepalive 不触发提交。首个有效事件前出现协议 `error`、非法帧、超时或断流时，按错误策略决定是否切换到下一渠道，不再次调用当前渠道。代理在提交点前不得向下游写 HTTP 状态、Header 或正文；默认最多缓冲 256 KiB 并受 `first_event_timeout` 限制，超过任一限制都按首事件前失败处理。提交后原样 Flush 已缓冲事件；之后发生错误只记录 `stream_interrupted`、结束连接并禁止切换渠道。

还必须处理：

- 客户端取消向上游传播。
- 下游断开立即取消上游请求。
- SSE 空闲超时和总时限。
- 有界缓冲和背压，禁止无限缓存响应。
- 服务关闭时停止接收新请求，并给予活动流可配置的优雅退出时间。

### 7.3 Responses 渠道亲和

当 Responses 请求包含 `previous_response_id` 时，优先查找本地保存的 `response_id -> channel_id` 关系：

- 亲和渠道可准入时只执行一次实际上游调用，不在其他渠道重放。
- 亲和渠道满载、冷却、自动禁用、半开名额已占用或调用失败时，返回可解释错误，不能静默切换到不认识该 ID 的渠道。
- 用户可在高级配置中明确选择“允许无状态 fallback”，但默认关闭。
- 亲和记录有独立保留期，且不保存响应正文。

## 8. 重试、错误分类与健康状态机

### 8.1 错误分类

V1 即保留结构化错误分类，而不是把所有失败存成字符串：

- DNS、连接、TLS 和网络中断。
- 连接超时、首字节超时、流空闲超时、总超时。
- 401/403 认证或权限错误。
- 404 路径或模型错误。
- 408/409/429 等可独立配置的响应。
- 5xx 上游错误。
- 空响应、非法 JSON、非法 SSE。
- 上游在流开始前或开始后主动断流。
- 客户端取消和下游断开。

每一类错误集中定义“是否切换下一渠道、是否计入连续失败、是否允许改变健康状态”。阶段 12 不开放逐错误类别的用户配置，避免产生难以解释的组合；默认规则如下：

| 错误                               | 切换下一渠道 | 默认健康影响                                  |
| ---------------------------------- | ------------ | --------------------------------------------- |
| DNS、连接、TLS、首事件前断流       | 是           | 计失败                                        |
| 连接、首字节和首事件超时           | 是           | 计失败                                        |
| 408、409、429、500、502、503、504  | 是           | 计失败；达到冷却条件时遵守更长的 `Retry-After` |
| 401 或明确认证失败                 | 是           | 计失败，按渠道阈值和互斥失败动作处理          |
| 403                                | 是           | 协议 Adapter 确认为权限/渠道错误时计失败      |
| 明确的 model not found             | 是           | 不计整个渠道失败，只记录当前模型不可用        |
| 本地已确认的 400/413/422           | 否           | 客户端请求错误，不影响渠道                    |
| 上游普通 400/422                   | 否           | 保留原错，不盲目切换                          |
| 客户端取消、下游断开               | 否           | 不影响渠道                                    |
| 流已提交后的上游断流               | 否           | 记录部分失败；仅确认是上游故障时计健康失败    |
| 本地账本、配置或凭证读取失败       | 否           | 本地错误，不影响上游渠道                      |

错误策略必须集中定义并通过临时测试验证，不采用散落在 Handler 或 Adapter 中的判断。即使在流提交前切换渠道，上游也可能已经计费；界面和文档必须提示重复计费风险，并在上游支持时透传或生成兼容的幂等键，但不能假定所有厂商都支持幂等。

### 8.2 连续失败的计数单位

每个渠道在同一逻辑请求内最多产生一个 Attempt。符合健康失败规则的 Attempt 失败后立即把该渠道连续失败值原子加一；并发满载、人工禁用、冷却、自动禁用、半开名额已占用等跳过结果不产生 Attempt，也不增加失败值。有效健康版本中的真实请求成功会清零真实请求连续失败值；渠道已经进入冷却、自动禁用或被人工重置后，旧 lease 的迟到成功不得恢复状态，迟到失败也不得重复延长新一代状态。

探针失败使用独立计数，是否影响真实请求健康状态由探针策略控制，避免一次低成本探针误杀正常渠道。

### 8.3 状态模型

人工状态与健康状态正交：

```text
admin_state: enabled | disabled
health_state: healthy | degraded | cooldown | half_open | auto_disabled
```

状态转换：

```text
healthy
  -> 渠道级失败但未达阈值 -> degraded
  -> 达到阈值且 failure_action=cooldown -> cooldown
  -> 达到阈值且 failure_action=auto_disable -> auto_disabled

degraded
  -> 真实请求成功 -> healthy
  -> 达到阈值且 failure_action=cooldown -> cooldown
  -> 达到阈值且 failure_action=auto_disable -> auto_disabled

cooldown
  -> 到期后首次准入或恢复探针领取验证 lease -> half_open

half_open
  -> 当前版本唯一探针或受控真实请求成功 -> healthy
  -> 失败 -> cooldown，并增加冷却级别

auto_disabled
  -> auto_recover=true 且探针达到恢复成功阈值 -> healthy
  -> auto_recover=false -> 等待用户手动重置自动状态

任意健康状态
  -> 人工禁用 -> admin_state=disabled，自动状态不再使其加入路由
```

半开状态在业务请求和探针之间共用一个验证 lease，防止冷却结束后大量请求同时击穿。冷却以渠道 `cooldown_seconds` 为基数指数退避，默认上限为 15 分钟并加入小幅随机抖动；上游 `Retry-After` 更长时必须遵守更长时间。冷却到期不直接标记健康，而是自动允许一次半开验证；验证成功才恢复，失败则再次冷却。`auto_disabled` 是系统状态，不等于人工禁用；只有渠道开启探针自动恢复且恢复探针连续成功达到阈值时才能自动解除。`auto_recover=false` 时只能由用户人工恢复系统健康状态。人工禁用优先级最高，恢复健康状态也不会把人工禁用改成启用。健康更新通过健康版本和 lease 版本进行原子校验，避免真实请求、探针和人工操作的迟到结果相互覆盖。

## 9. 主动探针

每个渠道具有独立探针策略：

- 是否启用以及是否允许自动恢复。
- 连通性探针或最小推理探针。
- 探针模型和最小请求正文。
- 周期、随机抖动、连接超时、首字节超时和总时限。
- 连续成功/失败阈值。
- 是否在启动时、冷却结束时执行。
- 探针失败是否延长冷却。

开启 `auto_recover` 时必须同时启用恢复探针；“关闭全部探针但开启自动恢复”属于非法配置，保存和导入时直接拒绝。连续成功阈值必须大于 0。

调度规则：

- 全局限制探针并发数。
- 同一渠道禁止探针重叠执行。
- 真正发往上游的探针与业务请求共用渠道并发上限；渠道满载时探针跳过本轮，不排队且不计探针失败。
- `cooldown` 到期后，探针与业务请求竞争同一个半开验证 lease，只有一个能够发往上游。
- 定时任务加入随机抖动，避免所有渠道同时请求。
- 人工禁用渠道默认不执行自动探针。
- 手动探针不改变人工状态；探针结果只按当前健康版本更新系统健康状态。人工恢复使用独立动作并写入操作日志。
- 探针数据和业务请求数据分开统计。

阶段 0 已将下列表名和关键职责冻结；阶段 1 的迁移脚本必须与本计划第 10 章的数据模型保持一致：

| 表                       | 主要职责                                                                                              |

设计要求：

- `requests` 与 `attempts` 分离，一次逻辑请求经过三个渠道仍然只算一个请求。
- `requests` 开始时先写入 `processing`，完成、超时、取消或部分流中断时更新同一行；每个 `attempts` 必须记录自己的上游渠道、模型、协议、状态和时间点。
- `runtime_logs` 与运行日志文件写入同一事件，数据库用于历史查询/SSE 补发，文件用于脱离管理页的本地排障。
- 配置变更使用事务，失败时整体回滚。
- SQLite 开启 WAL、合理的 busy timeout 和定期 checkpoint。
- 聚合表与明细日志保留策略分开，避免清理请求正文后 30 天图表丢失。
- p50/p95 不直接对小时分位数再次求分位数；小时聚合保存固定延迟直方图桶，查询窗口时合并桶后计算近似分位数。
- 正文以本地“先压缩、再分块加密”的内容文件保存，SQLite 只存引用和元数据，避免大型 SSE 正文持续膨胀数据库。

## 11. 日志、隐私和安全

### 11.1 请求日志内容与隐私策略

请求日志是一条客户端逻辑请求的总账，列表只显示一行；`attempts` 记录每一次真实上游调用。请求开始时立即创建 `processing` 记录，结束时更新最终状态和统计字段。

V1 固定保存请求/响应元数据和正文快照。设置只控制正文大小上限、磁盘配额、保留期和清理动作。必须按四个范围区分内容：

- 客户端请求头、客户端请求体。
- 每个 Attempt 实际发出的上游请求头、上游请求体。
- 每个 Attempt 收到的上游响应头、上游响应体。
- 最终返回给客户端的响应头、响应体。

正文和 Header 的保存规则：

- 数据库中保存加密后的原始内容，前端只通过管理 API 获取。
- `Authorization`、`x-api-key`、`api-key` 和渠道凭证在管理 API 返回时替换为 `***`。
- Cookie 和 Set-Cookie 在管理页面显示原始值；数据库仍随请求快照整体加密保存。
- 其他 JSON 字段暂不做通用关键词遮罩，避免破坏 Prompt、工具参数和模型输出的排查价值。
- 运行日志文件不得写入完整请求/响应正文或凭证原值。
- 相同请求体可通过内容哈希复用存储，但每个 Attempt 必须保存自身的渠道、模型、Header 和响应元数据。

正文保存限制：

- 请求体和响应体默认分别限制 `1 MiB`，在设置页独立调整。
- 请求头和响应头不设置单独的日志截断上限；仍受 Go HTTP 服务自身协议级限制。
- 超限只截断日志快照，不影响真实代理转发，并记录 `truncated`、原始大小和保存大小。
- 内容文件先压缩、再分块 AEAD 加密；临时文件从第一字节起就是密文，完成后校验并原子改名。
- SQLite 只保存内容引用、密钥引用、nonce、哈希、大小、压缩和截断状态。
- 磁盘配额超限时优先删除最旧正文，再按批次删除最旧明细；不得删除配置或聚合统计。

正文详情只能以转义纯文本或安全 JSON 查看器展示，不能将模型返回内容作为 HTML/Markdown 执行。

### 11.2 请求字段和 Attempt 账本

`requests` 保存一次客户端逻辑请求：

- `id`、协议、客户端原始模型、最终逻辑模型、最终状态、分组、首次渠道名称、开始/完成时间。
- 最终渠道、是否发生重试或 fallback、Attempt 数、总耗时。
- 输入、输出、缓存读取、缓存写入、思考 Token、总 Token。
- TTFT、TPS、缓存率和流式正常结束标记。
- 当前请求处理中，除时间、渠道、模型、分组和已产生字段外，其他字段显示 `—`。

`attempts` 保存每次上游调用：

- Attempt ID、请求 ID、序号、渠道 ID/名称/分组、协议、原始模型和实际模型。
- 开始时间、首字节时间、首个有效内容事件时间、完成时间、耗时。
- HTTP 状态、最终状态、错误分类、错误摘要、重试/切换原因和是否触发 fallback。
- 该 Attempt 的输入、输出、缓存、思考和总 Token，以及请求/响应内容引用。
- `streamEnded` 表示是否收到对应协议的正常结束事件。

固定状态：`processing`、`success`、`error`、`timeout`、`cancelled`、`partial`。列表使用 Semi `Tag` 区分颜色；详情抽屉从右侧出现，默认展开最终成功 Attempt，没有成功时展开最后一次 Attempt，其余 Attempt 折叠。

### 11.3 指标计算

- 上游明确返回的 usage 优先；缺失字段才计算。
- 总 Token 优先使用上游 `total_tokens`，否则使用输入 Token + 输出 Token。
- 缓存率为缓存读取 Token / 输入 Token；输入为 0 或缺失时为未知。
- TTFT 为请求开始到首个有效内容事件的高精度时间；没有可靠首事件时显示 `—`。
- 流式 TPS 为输出 Token /（首个有效内容事件到请求结束的有效时间）；缺少任一字段时显示 `—`。
- 非流式没有可靠首 Token 时间时，TTFT 和流式 TPS 显示 `—`，不伪造为 0。
- 指标使用高精度 `time.Duration`，不采用按整数秒截断的计算。
- New API 的 FRT/TPS 仅作为外部参考；其“首个非空 SSE data”和整数秒耗时存在语义及精度限制，OneAI 按协议有效事件和高精度时间实现。

### 11.4 后端运行日志文件

运行日志与请求日志分开，作为后端排障链路：

- 文件位置：数据目录下的 `logs/runtime.log`。
- 按天轮转为 `runtime-YYYY-MM-DD.log`，单文件默认上限 `100 MiB`。
- 默认保留 7 天；超过天数或大小的旧文件自动删除。
- 文件可读文本或 JSON Lines，至少包含时间、级别、事件、请求 ID、Attempt ID、渠道、模型、协议、状态和错误摘要。
- 记录启动/停止、监听器、数据库迁移、渠道候选选择、重试/fallback、探针、健康状态、超时、取消、数据库异常和清理结果。
- 不记录完整请求体、响应体、Authorization、API Key、Cookie 或其他凭证原值；凭证字段使用 `***`。
- 不增加敏感诊断模式，不允许通过管理 API 恢复运行日志中的凭证原值。
- 运行日志文件不进入配置迁移包、完整配置导出或数据库恢复快照。

前端“运行日志”通过后端 API 查看，不直接读取文件：首次加载最近 100 条，建立 SSE 接收新事件；用户上滚后暂停自动跟随，悬浮按钮回到底部后恢复。SSE 断线携带最后事件 ID 重连，无法补发时重新加载最近 100 条并提示可能存在缺失；前端最多保留最近 2,000 条可见记录。阶段 13 起 SSE 在当前管理令牌复核点建立可取消且绑定认证代次的订阅，不占长时间 operation lease；令牌换代或进入 draining 立即失效旧订阅，不再向旧连接选取新日志，已选取帧允许完成写出。新订阅在维护期返回 503；前端以当前令牌和游标重连，401 等待令牌更新或重新输入，503 遵循 `Retry-After`，长连接不得阻塞导入或恢复。

### 11.5 操作审计日志

操作日志只记录关键管理动作，不保存完整请求或正文：

- 渠道新增、编辑、复制、删除、启停和排序。
- 模型获取、添加、删除、清空和测试。
- 探针测试、健康重置、自动禁用和自动恢复。
- 模型同步、模型删除、全局映射保存。
- 监听、请求、日志、鉴权、导入、导出、备份、恢复和令牌轮换配置修改。
- 查看凭证、复制凭证等高风险读取操作。

列表字段为时间、操作类型、目标对象、结果、操作 IP 和操作者标识；失败和拒绝也必须记录。详情只展示脱敏后的关键变更，例如字段名、旧值和新值摘要；密钥、令牌、完整 Header、完整正文和 Cookie 值不得写入审计记录。审计记录追加写入，不提供编辑和单条删除。

### 11.6 日志查询、分页和清理

请求和操作日志均使用页码分页：

```json
{
  "items": [],
  "page": 1,
  "pageSize": 50,
  "total": 0,
  "hasMore": false
}
```

默认每页 50 条，可选 20/50/100；按时间倒序。请求筛选支持时间、模型名称、协议、状态、渠道、分组、错误分类、fallback 和关键词；操作筛选支持时间、分类、结果、目标关键词和操作 IP。列默认全部显示，列隐藏状态仅保存在浏览器本地缓存，不写入数据库。

默认保留期：请求日志 30 天、操作日志 30 天、运行日志 7 天。后台每天执行一次按时间戳扫描，只删除早于截止时间的数据和文件，不清空整张表；设置页同时提供按类型立即清理，并要求确认和显示预计删除数量。请求正文清理时同步删除关联内容引用和文件；聚合统计不因明细清理而丢失。阶段 13 起，自动/手动日志清理必须在任何副作用前取得覆盖整个调用（正文、父 Request、审计、运行日志及文件）的 maintenance operation lease；父行只在同一短事务复核终态、保留期、活跃引用、正文行与按 `requestId` 登记的未完成 journal 均为空，且与读取/capture pin 的登记在同一序列点互斥时删除。任何正文被 pin 跳过时必须保留父行，不能让 `ON DELETE CASCADE` 绕过 pin；恢复 draining 等待整个清理操作结束或超时零提交，不允许旧集合清理继续操作新库。

### 11.7 本地鉴权

- 管理令牌与代理令牌分开保存、可由用户自定义、轮换和撤销；首次启动使用本地默认令牌，用户保存自定义值后默认令牌失效。
- 默认禁止跨域访问管理 API。
- 管理 API 校验 `Host` 和 `Origin`，默认只允许明确配置的回环地址；拒绝未知 Host、跨站修改请求和 DNS rebinding 常见入口。
- 管理页面只使用显式管理令牌，不依赖浏览器 Cookie 自动鉴权；写操作仅接受预期的 `Content-Type`，降低 CSRF 风险。
- 管理页面设置严格 CSP，至少限制资源与连接为本地 `self`、禁止被第三方页面嵌入，并且运行时不加载外部 CDN 资源。
- 监听非回环地址时，界面显示明确风险提示并强制启用鉴权。
- 渠道凭证只允许在本地受管理鉴权保护的编辑会话中回显和复制；列表、日志、审计、诊断和安全导出不得出现明文。
- 导出默认使用不含密钥的 `safe` 模式；用户显式选择 `complete_encrypted` 后，全部可迁移配置、渠道凭证和管理/代理令牌统一放在口令加密载荷中。
- 审计日志和运行日志不包含秘密原值或完整正文；客户端代理凭证不转发上游，上游凭证不返回下游。

### 11.8 密钥存储

通过秘密存储 Adapter 隔离平台差异：

- Windows 优先使用 DPAPI 或 Credential Manager。
- macOS 使用 Keychain。
- Linux 优先使用 Secret Service。
- 不支持系统密钥环时，进入受限的本地加密模式并明确提示保护边界。

数据库中的渠道记录只引用秘密标识。便携包复制数据库时不会默认带走可直接使用的明文 API Key。

## 12. 统计口径

所有图表都必须明确指标口径：

### 12.1 逻辑请求指标

- 请求总数、最终成功率、最终失败率。
- 端到端总耗时 p50/p95。
- 发生 fallback 的请求数和比例。
- 客户端取消和最终流中断数。

### 12.2 渠道尝试指标

- 渠道实际尝试次数和成功率。
- 首字节/首事件耗时 p50/p95。
- 连接错误、超时、401/403、404、429、5xx 和非法响应次数。
- 跨渠道切换次数、并发满载跳过次数、冷却次数和自动恢复次数。
- 输入 token、输出 token、缓存读取 token、缓存写入 token。

### 12.3 探针指标

- 探针次数、成功率、延迟和最后成功时间。
- 自动恢复次数与恢复耗时。

### 12.4 请求实时与延迟指标

- 请求进入路由后立即计入 `processing` 数量；成功率、失败率、Token 汇总和平均耗时只统计已结束逻辑请求。
- 请求状态固定为 `processing`、`success`、`error`、`timeout`、`cancelled`、`partial`；已提交正文后断流属于 `partial`，不能记为成功。
- TTFT 使用请求开始到首个有效内容事件的高精度时间；无可靠首事件时为未知。
- 流式 TPS 使用输出 Token /（首个有效内容事件到结束的有效时间）；缺失 Token 或时间时为未知。
- 总 Token 优先使用上游 `total_tokens`，否则使用输入 Token + 输出 Token；缓存读取 Token 不重复累加。
- 缓存率使用 `sum(cache_read_input_tokens) / sum(input_tokens)` 的加权比例；输入 Token 缺失或为 0 时显示未知。
- 所有无法可靠计算的数值使用 `null`/“未知”/`—`，禁止用 0 代替未知。
- New API 的 FRT/TPS 只作为对照参考；本项目不复制其首个非空 SSE 数据事件和整数秒耗时的精度限制。

当天、7 天和 30 天通过相同聚合口径查询。时间窗口定义为用户时区下的日历窗口：当天从本地 00:00 到当前时间，7 天包含当天及之前 6 个日历日，30 天包含当天及之前 29 个日历日。数据库时间戳和小时桶统一存 UTC，查询时使用 IANA 时区数据库计算本地边界和夏令时，不使用固定 UTC 偏移。

成功和失败口径固定为：

- 逻辑请求“成功”必须收到非流式合法终止响应，或收到对应流式协议的正常终止事件。
- 已提交后断流记为 `partial`，计入失败分母并单独展示，不能记为成功。
- 成功率分母为已通过本地鉴权/校验并进入候选选择、最终状态为 `success | error | partial` 的逻辑请求；`cancelled` 和本地校验拒绝单独统计，不进入成功率分母。
- 渠道 Attempt 只有在协议正常终止时才算成功；仅收到首事件不算成功。
- fallback 请求比例 = 使用两个及以上不同渠道的逻辑请求数 / 至少启动过一个 Attempt 的非客户端取消逻辑请求数。
- 探针不进入业务请求和 Attempt 成功率。

缓存不强行归并为一个可能误导的“命中率”：

- 优先展示缓存读取 token / 总输入 token。
- 同时展示返回缓存字段的请求覆盖率。
- 上游没有提供缓存字段时显示“未知”，不能当作 0 或未命中。

跨请求缓存 token 比例按 `sum(cache_read_input_tokens) / sum(input_tokens)` 加权计算，不能平均每条请求的比例。延迟桶初始边界为 `[25, 50, 100, 250, 500, 1000, 2000, 5000, 10000, 30000, 60000, +Inf]ms`，端到端延迟和首事件延迟分别聚合；p50/p95 显示为近似值，允许误差不超过命中桶宽度，进入 `+Inf` 桶时只显示“超过 60s”而不伪造精确值。

## 13. 配置与数据管理

### 13.1 配置热更新

可热更新：

- 渠道启用状态、优先级和能力声明。
- 渠道模型与全局模型映射。
- 重试、fallback、冷却和探针参数。
- 日志正文大小上限、保留期、磁盘配额和运行日志文件策略。
- 管理令牌、通用代理令牌，以及迁移导入中除监听/数据目录外的运行快照。
- 主题和大部分管理页面设置。

需要重启：

- 代理监听地址和端口。
- 管理监听地址和端口。
- 数据目录和密钥存储初始化方式。

设置保存前应校验端口冲突，并清楚显示“立即生效”或“重启后生效”。

### 13.2 导入导出格式

项目自定义 JSON 格式必须带 Schema 版本：

```json
{
  "format": "oneai-proxy-export",
  "schemaVersion": 4,
  "exportMode": "safe",
  "exportedAt": "2026-08-27T00:00:00Z",
  "appVersion": "0.1.0",
  "channels": [],
  "channelModels": [],
  "globalModelMappings": [],
  "channelModelMappings": [],
  "probePolicies": [],
  "settings": {}
}
```

导出数组的元素结构、字段类型和校验规则以本节及第 10 章的数据模型为准；阶段 10 的 v5 载荷将全局映射升级为 `openai` 与 `anthropic` 两个单层对象，每个对象内部只使用模型名键值对。未列字段默认拒绝。`safe` 是默认明文导出，不能包含 `credential`、`tokens` 或任何密钥明文；`complete_encrypted` 使用 Argon2id + XChaCha20-Poly1305 信封，只有解密后同时带 `format`、`schemaVersion`、`exportMode` 和完整 `tokens` 的载荷允许包含渠道凭证。

导入流程固定为：文件解析 -> `complete_encrypted` 解密（完整模式）-> Schema 校验 -> 语义校验 -> 冲突检测 -> 脱敏差异预览 -> 创建同实例恢复点 -> 秘密存储暂存 -> 配置与令牌单事务写入。阶段 13 起，事务提交前失败清理本次暂存引用并保持原配置；事务提交后以数据库哈希/journal 为提交判定，只前滚到完整新集合，不自动恢复较早恢复点而丢失期间日志。导入前恢复点作为管理员显式回滚入口保留。需要检测重复 ID、未知协议、缺失渠道和重复模型映射。

配置导出与同实例恢复点是两个不同概念：

- `safe` 配置导出包含渠道、模型映射、探针策略和通用设置；不包含密钥、令牌、请求正文、明细日志、健康运行态和 Responses 亲和记录。
- `complete_encrypted` 在同一配置范围内包含渠道凭证、管理令牌和代理令牌；导入时整体解密并写入对应的本地配置和平台秘密存储，生成新的 `secret_ref`，因此导入完成后无需重新填写配置即可直接使用。
- 同实例恢复点包含一致性 SQLite 快照、仍在保留期内的加密正文文件、受实例命名空间保护的 secret bundle 和清单；过期亲和记录在恢复后清理。
- 同实例恢复点不写入平台主密钥明文，只支持在 namespace、SQLite binding、authority 和规范化真实路径均未变化的原路径绑定实例内回滚；数据目录丢失、换路径或 authority 损坏时不能用它重建实例。完整目录跨机器复制到相同绝对路径不受支持，但当前没有目录外机器身份，不承诺一定检测或拒绝这种复制。
- 升级前与导入前均创建同实例恢复点；恢复前校验数据库、正文、secret 引用、实例绑定和版本，再在显式维护状态中切换。跨设备配置迁移必须使用阶段 11 的带口令迁移包。

#### 阶段 10 导出版本扩展（目标 `schemaVersion: 5`）

阶段 0 冻结的 `schemaVersion: 4` 是当前已实现配置格式的基线，阶段 10 不在 v4 上偷偷追加字段。模型目录上线时整体升级到 v5；未知或旧的 v4 载荷直接拒绝，不做猜测性兼容或隐式迁移。v5 的 `safe` 与 `complete_encrypted` 载荷都包含非秘密的 `modelCatalog`，最近使用的单一在线源地址随 `settings` 迁移，完整模式仍额外携带渠道凭证及两个令牌。

```json
{
  "format": "oneai-proxy-export",
  "schemaVersion": 5,
  "exportMode": "complete_encrypted",
  "channels": [],
  "channelModels": [],
  "globalModelMappings": {
    "openai": {},
    "anthropic": {}
  },
  "channelModelMappings": [],
  "probePolicies": [],
  "modelCatalog": [],
  "settings": {},
  "tokens": {
    "adminToken": "<管理令牌>",
    "proxyToken": "<代理令牌>"
  }
}
```

`modelCatalog[]` 的稳定结构为 `stableKey`、`baseModelId`、`modelId`、`displayName`、`vendor`、`provider`、`protocol`、`modelType`、`description`、`modalities`、`capabilities`、`contextWindow`、`maxInputTokens`、`maxOutputTokens`、`pricing`、`currency`、`billingUnit`、`sourceType`、`sourceUrl`、`sourceAdapter`、`sourceVersion`、`sourceStatus`、`syncedAt` 和 `publishedAt`；其中 `stableKey`、`modelId`、`protocol`、`sourceType`、`sourceStatus` 为必填，`displayName` 可选，显示为空时前端使用 `modelId`，不凭空生成展示名称。数值费用和上下文字段必须为非负数。在线记录必须带公开源 URL 和已注册 Adapter；不保存远端原始响应正文或认证 Header。导入先校验稳定键唯一、协议合法、来源状态合法、费用结构和在线来源字段，再进入现有差异预览、备份、单事务写入和失败回滚流程。

模型目录属于可迁移配置但不属于代理请求白名单；导入或删除模型目录不得修改渠道、渠道模型、任一层模型映射、探针策略或日志。模型目录来源已移除状态随配置迁移，导入不会自动删除失效记录。配置导入不是 SQL 导入：应用会先解析、校验、预览并在事务内写入当前 SQLite；用户不需要也不应手动执行导出的 SQL。

同实例恢复点是独立的本机回滚能力，包含一致性 SQLite 快照、保留期内的加密正文文件、受实例命名空间保护的 secret bundle 和哈希清单，不等同于配置导出，也不是通用灾备。恢复由应用校验版本、清单、实例绑定、秘密引用和文件后在显式维护状态中执行；不能只复制数据库或只执行 SQL。现有 `/config/backup*` HTTP 路径为兼容接口路径，UI、manifest 和文档统一使用“同实例恢复点”语义。

#### 阶段 11 跨平台完整迁移包（实施计划）

**目标与用户体验**

阶段 11 新增独立的“导出迁移包”和“导入迁移包”操作。用户在源电脑输入一次导出口令即可得到一个单文件迁移包；在目标电脑选择该文件并输入口令，完成预览和显式确认后，所有可迁移配置、渠道凭证和管理/代理令牌一次性写入目标环境。阶段 13 migration v2 导入完成后，除监听地址/端口外的新配置和两个令牌立即生效；仅当监听设置发生变化时提示用户重启以切换监听。不要求安装 Go、Node.js，不要求手动复制数据库、配置文件或操作系统密钥环。

迁移包默认采用“完整替换可迁移配置”语义，而不是与目标配置猜测性合并。导入预览必须先展示渠道、模型、映射、探针、监听设置和令牌是否存在，以及将被替换的配置数量；用户确认后才允许写入。为避免 SQLite 外键级联删除目标机日志，导入不能简单删除并重建全部渠道：同 ID 渠道按事务内更新，导入中不存在但仍被目标机日志引用的旧渠道保留为已禁用占位并清理秘密引用；只有没有任何日志引用的旧配置才允许删除。目标机当前的请求日志、Attempt、统计和审计记录不被迁移包覆盖，也不因导入而导出到包内。

**单文件格式与加密**

迁移包使用独立于配置导出的格式和扩展名，例如 `.oneai-migrate`。外层是 UTF-8 JSON 信封，信封只包含版本、应用元数据、KDF 参数、加密算法、压缩编码和密文，不出现任何令牌、渠道密钥、路径或日志内容：

```json
{
  "format": "oneai-proxy-migration",
  "migrationVersion": 1,
  "exportedAt": "2026-08-31T00:00:00Z",
  "appVersion": "0.1.0",
  "configSchemaVersion": 5,
  "databaseSchemaVersion": 21,
  "payloadEncoding": "gzip+json",
  "kdf": {
    "algorithm": "argon2id",
    "salt": "base64",
    "memoryKiB": 65536,
    "iterations": 3,
    "parallelism": 2
  },
  "cipher": {
    "algorithm": "xchacha20-poly1305",
    "nonce": "base64"
  },
  "ciphertext": "base64"
}
```

载荷先以 JSON 序列化并 gzip 压缩，再使用 Argon2id 从用户口令派生 32 字节密钥，最后用 XChaCha20-Poly1305 整体加密。外层 `migrationVersion` 与内部 `configSchemaVersion` 分开校验；口令不落盘，AEAD 认证失败即视为口令错误或文件被篡改。实现需限制信封大小、解压后大小、解压比例和解析耗时，避免异常文件占满资源。

**迁移载荷白名单**

解密后的载荷使用当前最新配置契约（阶段 10 为 `configSchemaVersion: 5`），只允许以下字段：

```json
{
  "format": "oneai-proxy-migration-payload",
  "migrationVersion": 1,
  "configSchemaVersion": 5,
  "databaseSchemaVersion": 21,
  "settings": {},
  "channels": [],
  "channelModels": [],
  "globalModelMappings": {
    "openai": {},
    "anthropic": {}
  },
  "channelModelMappings": [],
  "probePolicies": [],
  "modelCatalog": [],
  "tokens": {
    "adminToken": "<管理令牌>",
    "proxyToken": "<代理令牌>"
  }
}
```

迁移包包含所有可直接影响代理行为或管理页面的配置：监听地址和端口、请求/重试/冷却策略、日志策略设置（只迁移策略，不迁移日志）、渠道基本信息、凭证类型和自定义请求头、渠道模型、渠道级映射、全局 OpenAI/Anthropic 映射、兜底模型、优先级、分组、并发和 `service_tier` 设置、探针策略、模型目录及两个本地令牌。`secret_ref`、数据库绝对路径、目标机数据目录、锁文件和平台相关元数据不得进入载荷；渠道凭证必须只以完整载荷内的秘密字段携带。

以下内容明确不导出、不导入：`requests`、`attempts`、`health_runtime`、`health_events`、`probe_runs`、`response_affinity`、`audit_logs`、`hourly_metrics`、`content_blobs`，以及 `content/` 下的加密正文文件、SQLite 的 `-wal`/`-shm` 临时文件、缓存、运行 PID 和任何日志文件。目标机原有日志保留在目标机；新导入配置产生的日志从导入完成后的新请求开始记录。阶段 13 migration v2 的目标运行态另按替换事务处理：普通渠道获得新 identity 时初始化当前健康运行态，不继承同 id 旧渠道的故障；日志占位渠道保留原健康字段，历史 Request/Attempt、health_events、probe_runs 不因初始化被删除或改写；response_affinity 按整包替换规则清空。上述运行态处理不等于把源机运行态装入迁移包。

**目标机恢复与事务边界**

导入顺序固定为：读取外层信封并做大小限制 -> 解密和解压 -> 校验迁移版本、配置版本、数据库版本和全部字段 -> 校验渠道/模型/映射/探针语义 -> 生成脱敏预览 -> 用户显式确认 -> 创建当前配置恢复点 -> 为每个渠道凭证和列表密钥生成新的 `secret_ref`，先通过 `SecretRefLifecycle` 持久登记 `import_provisional` 并取得 operation lease，再写入目标机密钥环 -> 在单个 SQLite 事务中按 ID 更新/新增渠道、保留日志引用渠道占位、替换其他可迁移配置和两个令牌，同时移除已引用的新 provisional 项并把未被新配置引用的旧秘密登记为 `import_superseded` -> 提交 -> journal 前滚并按 ref 级 lease/引用条件清理旧秘密。provisional 记录先于密钥环写入；事务提交前失败保持旧集合，提交后按阶段 13 journal 只前滚到完整新集合。成功响应不得回显 token 明文，但必须把新管理/代理令牌封装进由提交前管理 Bearer 派生、绑定本次 opId/requestId 的一次性 `authTokenHandoffEnvelope`，供当前管理页原子切换本地令牌；浏览器持久化只使用严格 `PendingAuthTokenHandoffV1`，固定含 `version=1`，不接受无 version 对象或裸字符串。阶段 11 的当前实现记录不改写历史，但阶段 13 的 migration v2 不再用自动恢复较早快照作为普通失败路径。

导入不会复制源电脑的 `secret_ref`，也不会要求目标电脑拥有源电脑的密钥环；目标平台通过 Windows、macOS 或 Linux 的秘密存储 Adapter 写入新引用。目标机的操作系统、CPU 架构和数据目录可以不同，但迁移包只携带逻辑配置和标准化秘密，不携带平台路径或二进制数据。监听地址和端口仍在重启后生效，现有进程继续使用旧监听；阶段 13 migration v2 中的管理令牌、通用代理令牌和运行目录快照必须在事务提交、固定 live secret 前滚和内存快照发布全部成功后**立即生效**，旧令牌同时失效。前滚或内存发布无法完成时进程必须 fail-closed，不能继续用旧令牌接收请求。

错误口令、AEAD 校验失败、文件被篡改、未知 `migrationVersion`、不支持的配置/数据库版本、重复渠道 ID、重复映射、跨协议映射、无效 URL、非法端口或秘密存储不可用，都必须在写入前返回可解释错误。导入预览和错误信息不得回显任何密钥、令牌或完整请求正文。

**与现有能力的关系**

- `safe` 配置导出：用于分享非秘密配置，仍不包含任何密钥或令牌。
- `complete_encrypted` 配置导出：用于当前配置 Schema 的加密导入导出；阶段 10 继续升级到 v5。它可恢复配置和秘密，但不承担阶段 11 对跨平台单文件迁移、目标机密钥环重建和日志保留的完整验收承诺。
- 同实例恢复点（现有 `/config/backup*` HTTP 路径后续由阶段 13 统一语义）：包含 SQLite 快照、加密正文和受实例秘密命名空间保护的 secret bundle，只支持在原路径绑定实例内回滚，不能覆盖数据目录丢失、换路径或 authority 损坏；跨机器同路径复制不受支持且不保证可检测，不得再称为通用灾备或机器绑定能力。
- 阶段 11 迁移包：面向不同电脑和操作系统的一键配置迁移，逻辑上替换目标机可迁移配置；按 ID 更新渠道并保留日志引用的禁用占位，永不携带请求日志和正文，也不接受 SQL 文件作为输入。

当前范围没有“可携带且包含请求日志/正文的完整灾备”。如后续需要，必须另立阶段设计带口令的可携带数据库、正文与秘密封装，不能把阶段 11 迁移包或同实例恢复点宣传成该能力。

**阶段 11 验收与执行顺序**

1. 先实现独立迁移信封、压缩/加密、严格版本校验和白名单载荷，使用临时文件验证错误口令、篡改文件、超大文件和未知版本均无写入。
2. 实现配置快照、目标机密钥环暂存、新 `secret_ref` 生成、SQLite 单事务替换、失败清理和重启标记。
3. 接入管理页面的一键导出、文件选择、口令输入、脱敏预览、显式确认、进度和结果 Toast；不把日志数据放进迁移页面的可选项中。
4. 在空数据目录和已有数据目录分别验证导入；已有目录中的请求日志、Attempt、统计、审计和正文保持不变，导入后新请求使用迁移后的配置。
5. 在 macOS、Windows、Linux 的不同架构发布包中交叉导出/导入，验证无需 Go、Node.js、源数据库或源密钥环即可启动管理页并成功代理三种协议。
6. 完成 `go test ./...`、`go vet ./...`、`npm run typecheck`、`npm run build`、`git diff --check` 以及阶段 11 临时跨平台反馈环；通过后删除临时测试文件并回填执行记录。

## 14. 前端信息架构

管理页采用顶部主导航，不使用常见的深蓝色固定侧边栏。主页面包括：

6. **设置**：监听、超时、重试、冷却、日志保留、鉴权、主题、全局模型映射、导入导出和数据恢复。

## 16. 技术选型与目录规划

### 16.1 后端

- Go 标准库 HTTP 能力为主，避免引入大型 Web 框架。

- 使用 CSS 自定义属性管理浅暗主题，普通 CSS 或 scoped CSS 实现布局。
- 静态资源全部随发布包提供，管理页面运行时不依赖外部 CDN。

### 阶段 4：重试、fallback 与健康状态机

**请求日志 API**

```text
GET /api/admin/v1/logs/requests
GET /api/admin/v1/logs/requests/{requestID}
GET /api/admin/v1/logs/stats
```

请求列表使用 `{items, page, pageSize, total, hasMore}`，默认每页 50 条，可选 20/50/100，按开始时间倒序。支持时间、模型名称、协议、状态、渠道、分组、错误分类、fallback 和关键词筛选。详情从右侧抽屉展示摘要、Attempt 时间线及折叠的请求头/请求体/响应头/响应体。

列表默认字段为请求时间、原始渠道名称、模型（无映射显示单名，有映射显示 `A -> B`）、状态 Tag、协议、分组、输入/输出/缓存/思考/总 Token、缓存率、TTFT、TPS、耗时、详情。原始渠道有重试时显示标记，悬浮展示渠道链路；列显隐保存在浏览器本地，不进入数据库。

**运行日志 API 与文件**

```text
GET  /api/admin/v1/logs/runtime?limit=100
GET  /api/admin/v1/logs/runtime/stream   # SSE，支持 Last-Event-ID
```

进入页面首次读取最近 100 条，然后建立 SSE。默认显示 `info/warn/error`，可筛选 `debug`；用户向上滚动后暂停自动跟随，悬浮按钮滚到底部后恢复。断线按最后事件 ID 补发，无法补发时重新读取最近 100 条并提示可能缺失；前端最多保留 2,000 条可见记录。

运行日志文件位于数据目录 `logs/runtime.log`，按天轮转并设置默认 `100 MiB` 单文件上限，默认保留 7 天。记录启动停止、监听、迁移、路由、Attempt、重试、fallback、探针、健康状态、超时、取消、数据库异常和清理结果。文件不加密，但完整请求/响应正文以及 API 凭证、Cookie 原值不得写入，敏感凭证统一为 `***`。

**操作日志 API**

```text
GET /api/admin/v1/logs/audit
```

使用同样的分页结构，支持时间、分类、结果、目标关键词和操作 IP 筛选。分类包括渠道、模型、探针、设置、导入导出和安全；成功、失败、拒绝和高风险读取都要记录。详情只显示关键脱敏变更，不显示密钥、令牌、完整 Header、正文或 Cookie。

**清理与设置**

- 请求日志保留 30 天，操作日志保留 30 天，运行日志保留 7 天。
- 后台每天执行一次按时间戳扫描，只删除超过期限的行、正文引用和轮转文件，不清空整张表。
- 设置页提供三个独立保留期、请求/响应正文各自大小上限（默认各 `1 MiB`）、磁盘配额和立即清理动作；V1 固定记录正文。
- 手动清理显示预计数量并要求确认；清理结果写入运行日志，失败不影响代理请求。
- 过期明细删除后，小时聚合和保留期内统计继续可查询；日志文件不进入迁移包或配置导出。

### 阶段 10：模型目录管理

**目标**

新增一个顶部“模型”菜单，提供跨渠道的模型资料目录、在线源同步预览、详情查看和手工模型维护。全局模型映射位于“设置”菜单的映射区域。模型目录只服务于展示、搜索、费用参考和渠道编辑时的模型联想，不作为代理白名单，不参与渠道候选过滤，也不改变当前请求的兜底和容灾顺序。

**明确不做**

- 不以模型目录限制或拒绝代理请求。
- 不把在线目录当作某个渠道实时可用模型列表；渠道实际可用模型仍由渠道模型目录和渠道映射决定。
- 不提供模型库 JSON 导入；手工模型通过新增弹窗创建。
- 不做计费、扣费、价格路由或按费用排序。费用字段为未来统计保留原始单位和来源。
- 不自动修改渠道模型、渠道映射、全局映射或渠道优先级。
- 不支持需要认证 Header 的私有在线源；第一版只读取公开 HTTP(S) JSON。

**页面与交互**

桌面和移动端均采用模型目录单列表布局，列表在页面中占满除标题、筛选和分页之外的剩余高度并独立滚动；全局映射不再占用模型页面空间。页面使用现有顶部导航、Semi 组件和 Apple 风格令牌，模型数量增长不会造成额外纵向滚动。

模型库工具栏包括搜索、协议/厂商/模型类型/能力/来源筛选、刷新、同步模型、新增模型、删除。主表始终按单条模型记录展示模型名称、协议、厂商/供应商、模型类型、能力、上下文、最大输出、输入/输出费用、来源状态和更新时间；模型名称只显示一次，真实模型 ID 在详情中查看。列表不做分组、折叠或展开，支持分页、表头拖拽列宽缓存和固定右侧操作列。每行提供详情查看和编辑入口；详情显示真实模型 ID、模态、各项费用、发布时间、最近同步时间和稳定键；任意来源记录均可编辑和勾选删除。在线记录编辑时保留来源元数据，服务供应商保持只读，模型 ID 和协议按手工模型规则可编辑并随之重算稳定键。费用显示币种、计费单位和原始精度。

新增模型使用弹窗。必填字段为模型 ID 和协议；显示名称可选，缺失时使用模型 ID 展示。其余可选字段为基础模型名、模型厂商、服务供应商、模型类型、描述、输入/输出模态、能力、上下文长度、最大输出、发布时间、输入/输出/缓存费用、费用币种、计费单位和来源备注。保存前校验协议、模型 ID、非负数值和费用单位，默认来源为“手工新增”。手工记录和在线记录均可继续编辑或确认删除；在线记录通过同步预览选择性更新。

渠道编辑页的模型选择器先按当前渠道协议过滤，再只对模型 ID 和显示名称执行文字模糊匹配；不按能力、厂商或模型类型过滤，也不提供“显示全部”开关。模型资料能力只作为标签展示，不参与联想筛选。无明确协议的在线记录保留在模型库，但不进入渠道联想结果，用户可通过新增弹窗手工指定协议。

**在线源与解析适配**

默认在线源为 `https://models.dev/catalog.json`。每次打开同步弹窗都填入该默认地址，一次只接收一个地址，同时提供恢复默认源；不提供多源列表或定时同步。第一版只接受公开 HTTP(S) JSON，限制响应大小和请求超时，拒绝重定向到非 HTTP(S) 或无法解析的内容。

解析器采用明确的 Adapter 列表，不递归猜字段：

1. `models.dev/catalog.json`：读取顶层 `models` 基础资料，并与 `providers.<provider>.models` 的供应商版本合并，提取真实模型 ID、供应商、能力、模态、上下文、限制和 `cost` 字段；同一基础模型的供应商版本保持为独立目录记录。
2. OpenAI 兼容目录：读取 `data[].id`，兼容 `object=list`，只产生模型 ID 和可确认的协议/来源字段。
3. 常见兼容目录：读取 `models[].id`。
4. CCH Plus：读取 `models[].model_name` 作为渠道候选名称、`slug` 作为稳定标识，并保存厂商、模型类型、端点、模态、能力和费用。

未知结构返回“无法识别模型源格式”，不得从任意嵌套字段中猜测模型。解析结果先在预览弹窗中展示总数、可识别数、跳过数和错误摘要；单条记录错误不应静默变成空模型。

**协议归类与稳定键**

稳定匹配键为 `(protocol, provider, model_id)`。其中 `model_id` 是供应商实际模型 ID，`provider` 是服务供应商，不使用展示名称作为唯一键。只有来源中存在明确协议字段或 Adapter 能从明确端点元数据确认时，才归类为 `openai_chat`、`openai_responses` 或 `anthropic_messages`；单凭 `data[].id`、`models[].id` 或“OpenAI-compatible”名称不能判断 Chat 或 Responses，统一标记为 `protocol_unconfirmed`，只在模型库展示。来源类型固定为 `online`（在线同步）或 `manual`（手工新增），来源状态固定为 `valid`、`retired` 或 `protocol_unconfirmed`；仅当 `protocol=protocol_unconfirmed` 时允许使用 `sourceStatus=protocol_unconfirmed`，手工记录必须指定三种正式协议之一并以 `valid` 为初始状态。

模型主表始终按稳定键展示单条记录，不按 `base_model_id` 聚合，也不提供折叠或展开行；稳定键不改变渠道实际请求模型。

**同步、差异和失效处理**

同步流程固定为：请求远端 JSON -> 解析并标准化 -> 展示候选预览 -> 用户搜索、单选或全选当前页 -> 计算本地差异 -> 用户确认 -> 事务写入选中记录。预览默认不选中记录；搜索、翻页和选择只在前端内存中执行，列表区域独立滚动，分页始终固定显示在弹窗底部。

预览必须分别显示新增、字段变化、无变化、冲突、协议未确认和远端已移除。只有用户勾选的记录允许新增或替换；未勾选的本地记录保持不变。来源类型包括“在线同步”和“手工新增”，来源状态包括“有效”“来源已移除”和“协议未确认”。在线记录再次同步时只覆盖用户明确选择的记录；手工新增不受在线覆盖。

远端不再返回的在线记录只标记“来源已移除”，不立即物理删除；“远端已移除”只在相同规范化来源 URL 和相同 Adapter 的两次同步之间计算，切换在线地址不得把其他来源的记录标记失效。模型库工具栏提供“删除”，可删除用户勾选的任意模型并支持跨页保留选择。删除前显示影响数量；删除模型不会删除渠道模型、渠道映射、全局映射或日志。在线同步模型可以查看详情、编辑和删除；编辑保留在线来源元数据，下一次同步只在用户明确选择对应差异时覆盖本地修改。

**存储建议**

阶段 10 已将 SQLite schema 从 v17 增量升级为 v18。新增 `model_catalog` 表保存标准化记录，至少包含：稳定键、基础模型 ID、模型 ID、显示名称、厂商、服务供应商、协议、模型类型、描述、输入/输出模态、能力 JSON、上下文/最大输入/最大输出、费用 JSON、币种、计费单位、来源类型、来源地址、来源 Adapter、来源版本、来源状态、同步时间以及创建和更新时间。最近使用的单一在线源地址继续保存到 `app_settings`。对目录稳定键建立唯一约束，对协议和来源状态建立查询索引；大段描述和远端原始响应不落库。v18 迁移可重复执行，在已有 v17 数据上只增量新增表和索引，不改写渠道、映射、探针及历史日志。全局模型映射仍由设置页接口和配置导入导出维护，不属于模型目录页面。

同步预览不直接写库。确认后在一个事务内写入选中记录、更新来源状态和同步元数据，并记录脱敏审计事件。请求超时、JSON 无效、校验失败或事务失败时不得产生部分写入。

**全局映射 JSON**

全局映射提供两个 JSON 编辑区，分别属于 `openai` 与 `anthropic` 协议族；每个编辑区内部固定为 `客户端模型 -> 逻辑模型` 的扁平对象，目标模型不要求存在于模型目录。OpenAI 编辑区同时服务 `openai_chat` 与 `openai_responses`，Anthropic 编辑区服务 `anthropic_messages`。两个编辑区的空值均显示 `{}`。例如：

```json
{
  "modelA": "modelB"
}
```

运行时只在当前请求对应的协议族内做一次键查询：请求 `A` 若存在 `A -> B` 则得到 `B`，不会继续查 `B -> C`；请求原始模型 `B` 时才独立得到 `C`。保存和导入校验拒绝空键、空值、非字符串值、自映射和重复键；不接受把 `openai_chat`、`openai_responses`、`anthropic_messages` 或其他协议字段嵌套到 JSON 中。路由仍先按请求协议筛选渠道，渠道级映射继续要求精确协议与渠道一致，因此两个全局编辑区不会造成跨协议转发。

每个编辑器各自使用一个“保存映射”动作校验并提交，只替换当前协议族，另一个编辑区保持不变；失败时当前协议族整组不写入。保存成功后显示映射数量；请求日志继续记录请求协议、协议族、客户端模型、全局解析后的逻辑模型以及渠道最终上游模型。

**后端接口接缝**

建议将模型目录能力收敛到少量稳定接口：

```text
GET  /api/admin/v1/models/catalog                 # 分页、筛选、排序
POST /api/admin/v1/models/preview                 # 读取 URL、解析并返回预览，不写库
POST /api/admin/v1/models/apply                   # 提交勾选差异，事务更新
POST /api/admin/v1/models                         # 手工新增
PUT  /api/admin/v1/models/{stableKey}             # 编辑模型目录记录
DELETE /api/admin/v1/models/{stableKey}           # 删除单条模型目录记录
DELETE /api/admin/v1/models/batch                 # 删除用户勾选的模型目录记录
DELETE /api/admin/v1/models/retired               # 兼容旧接口：删除用户勾选的失效记录
GET  /api/admin/v1/models/global-mappings         # 返回 {"globalModelMappings":{"openai":{},"anthropic":{}}}
PUT  /api/admin/v1/models/global-mappings         # body 为 {"protocolFamily":"openai|anthropic","mapping":{"modelA":"modelB"}}，只替换该协议族
```

模型目录 Adapter、差异计算、稳定键、协议归类和校验应位于后端模块内部；前端只负责筛选、预览选择和表单状态，不复制同步规则。渠道编辑的模糊联想可以读取分页目录接口，并传入当前渠道协议和搜索词。

**导入导出与升级**

完整加密配置导出升级到 schema v5，增加模型目录、来源状态和 OpenAI/Anthropic 两组全局映射对象；safe 导出继续不包含秘密。导入 v5 前先校验模型目录稳定键、协议、费用数值、来源记录以及两个映射对象的键值，再与渠道、映射、探针配置一起执行现有差异预览、备份、单事务写入和失败回滚。v4 或未知主版本直接拒绝；导入不会携带远端原始响应正文，也不会把失效模型自动删除。配置导入写入应用当前 SQLite，不接受 SQL 脚本作为配置格式。

**阶段 10 验收**

1. 默认 `models.dev/catalog.json` 能成功预览并识别模型、协议、能力、模态和费用；未知格式会明确失败。
2. OpenAI `/v1/models`、`models[].id` 和 CCH Plus `model_name/slug` 示例均能按适配器产生正确预览；不会把空 `id` 写入目录。
3. 预览勾选新增和变化记录后，只替换勾选项；未勾选项、手工新增和渠道配置保持不变。
4. 远端消失记录会标记失效；删除处理用户勾选的任意模型，且不影响渠道模型、映射和日志。

### 阶段 12：路由容灾与并发准入重构

**目标与覆盖关系**

本阶段修正阶段 4/5 已实现但不符合当前产品语义的同渠道重试和阻塞式并发限制。阶段 12 完成后，以本节为重试、并发、健康状态和恢复行为的最新契约；阶段 4/5 的执行记录只保留为历史，不再作为当前行为依据。

目标行为固定为：候选按渠道优先级降序排列；每个逻辑请求对每个渠道最多发起一次实际上游调用；失败后立即完成该渠道健康结算并切换下一渠道；渠道满载时不排队，直接跳过；独立的新请求仍从最高优先级渠道开始，只要该渠道当时可准入。

本阶段继续采用单实例架构。渠道并发数保存在进程内存，健康状态和日志保存在 SQLite；不引入 Redis、分布式 lease、多实例共享健康状态或共享日志存储。

**现有配置盘点与最终取舍**

| 配置 | 现状 | 阶段 12 决策 |
| --- | --- | --- |
| `priority` | 已有并已按降序排序 | 保留；相同优先级继续按 `created_at ASC, channel_id ASC` 稳定排序 |

| `requestTimeoutMs` | 已有 | 保留；只约束当前渠道的一次上游调用 |

新建渠道的默认值保持克制：优先级 `100`、并发上限 `8`、请求超时 `120000ms`、流空闲模式默认“继承全局”（渠道覆盖值可初始化为 `300000ms`，但只有显式切换为 `override` 后才参与运行）、连续失败阈值 `3`、失败动作“进入冷却”、冷却基数 `30s`、探针默认关闭、探针自动恢复默认关闭、恢复成功阈值 `1`。全局最大渠道尝试数默认 `0`，即在逻辑请求总超时内遍历全部合格候选。

**运行时准入模块**

建立单一深模块承接健康判断和并发占位，外部接口概念固定为：

```text
TryAcquire(candidate, purpose, now) -> lease | skip decision | local error
lease.Finish(outcome, now) -> health result
Reset(channel, operator, now) -> health result
```

- `purpose` 只区分业务请求、自动探针和手动探针；三者共用渠道硬并发上限。
- `TryAcquire` 不等待。它在一个进程内临界区中重新读取人工状态、健康状态、健康版本和当前配置，再检查并发计数。
- 成功返回的 lease 至少携带渠道 ID、唯一 token、准入健康版本、是否为半开验证、准入时并发数和上限。
- lease 的释放必须幂等；调用方在领取后立即设置兜底释放，账本初始化失败、请求构造失败、客户端取消、超时、正常完成和异常退出均不能泄漏名额。
- `Finish` 先按集中错误策略生成 `success`、`health_failure`、`neutral_failure` 或 `not_sent`，再释放并发名额；只有匹配当前健康版本的结果可以改变健康状态。
- 进程重启后内存在途数归零是正确行为，因为数据目录锁保证旧实例已经退出；健康状态继续从 SQLite 恢复。
- 配置把并发上限调低到当前在途数以下时，既有请求允许结束，新请求持续跳过，直到在途数低于新上限；调高后新容量立即生效。
- 容量满载只是负载状态，不是健康失败，不创建 Attempt，不增加失败次数，也不生成 `busy` 健康状态。
- 健康存储不可读写属于本地错误，当前逻辑请求失败关闭，不能把数据库错误当成普通候选跳过后继续重放。

当前 `acquireChannelSlot` 使用有缓冲 channel 等待，并在并发上限热修改时替换 channel；阶段 12 必须用“渠道 ID -> 当前在途整数”的运行态替代，避免等待、替换旧 channel 和释放到错误容器的问题。当前 `forwardAPI` 持有长时间 `dataMu` 读锁，实施时改为短时读取不可变候选快照；真正发送前的准入始终读取最新运行状态，新配置只影响新 lease，不终止已有请求。

**优先级、并发溢出与跨渠道重试**

一次普通逻辑请求的执行顺序固定为：

```text
生成 A、B、C 有序候选
  -> A TryAcquire
     -> 满载/冷却/禁用/半开已领取：记录 skip，继续 B
     -> 成功领取：创建 Attempt，调用 A 一次
        -> 成功：结算并结束
        -> 可切换失败：原子结算 A，记录 A -> B，继续 B
        -> 不可切换失败或流已提交：结算并结束
  -> B、C 使用相同规则
  -> 全部候选耗尽：返回可解释终态和 request_id
```

- 一个请求内维护已实际尝试渠道集合，任何路径都不能再次调用同一渠道。
- `maxChannelAttempts` 只统计真正发出的 Attempt；满载和状态跳过不占用次数。
- 不同逻辑请求互不继承“尝试过”集合。A 在阈值前仍为可准入的 `degraded` 时，下一请求仍先尝试 A。
- A 的失败健康结算必须在尝试 B 前完成；若 A 达到阈值，其他新请求立即观察到冷却或自动禁用状态并跳过 A。
- 并发上限为 A=`2` 时，最多两个实际请求同时占用 A；其余请求立即尝试 B。A 任一请求结束并释放后，下一个新请求重新有机会使用 A。
- 所有候选都因满载被跳过且没有发出 Attempt 时，返回 `503 all_channels_busy`，并给出短 `Retry-After`；结构上没有匹配协议、模型或能力的渠道仍返回 `422 no_matching_route`。
- 已经产生失败 Attempt、随后剩余候选均不可准入时，保留最后一次上游错误作为主错误，同时在请求详情记录后续跳过原因。
- 达到实际尝试预算但仍有候选时，以 `attempt_budget_exhausted` 结束；不能伪装成渠道故障。
- Responses `previous_response_id` 只允许亲和渠道。亲和渠道满载返回 `503 affinity_channel_busy`，状态不可用返回 `503 affinity_channel_unavailable`，调用失败返回该次失败；三种情况都不切换渠道。

**健康版本、失败计数和状态转换**

- 健康版本代表一代可接受结果的运行状态。进入 `cooldown`、`half_open`、`auto_disabled`、人工恢复以及会改变路由/健康语义的渠道配置更新时递增版本。
- `healthy` / `degraded` 同一版本内的并发失败按完成顺序原子累加；同一版本内在达到阈值前完成的真实成功可以清零连续失败。
- 某次失败达到阈值后只允许一个事务执行状态转换并递增版本。旧版本仍在途的成功不得解除冷却或自动禁用，旧失败不得继续增加冷却级别。
- 人工禁用与系统健康状态正交。人工禁用立即阻止新 lease，但不取消在途请求；其迟到结果只完成日志和名额释放，不得改变人工状态。
- 修改失败动作、失败阈值、冷却基数、上游地址或凭证时递增健康版本，使旧请求结果失效；配置保存本身不根据旧计数立即触发新动作，新规则从下一次有效结果开始执行。

失败动作严格互斥：

1. `cooldown`：达到阈值后进入冷却。冷却时长为 `min(cooldownSeconds * 2^(level-1), 15 分钟)`，加入最多 10% 抖动；若当前失败携带更长的 `Retry-After`，最终时间取更长值。
2. 冷却到期不直接恢复为 `healthy`。下一次业务准入或恢复探针可以原子领取唯一半开 lease 并进入 `half_open`，其他请求跳过。
3. 半开验证成功后恢复 `healthy` 并清零业务失败数、冷却级别和恢复探针计数；失败后增加冷却级别并再次进入冷却。
4. 半开 lease 在实际上游调用前被取消或本地失败时，只释放领取，不计渠道失败，允许后续验证重新领取。
5. `auto_disable`：达到阈值后进入 `auto_disabled`，没有到期时间，业务请求始终跳过。
6. `auto_disabled` 且开启“探针自动恢复”时，自动探针继续按间隔执行；当前健康版本内连续成功达到 `recoverySuccessThreshold` 后恢复 `healthy`。任一恢复探针失败会把连续成功数清零，但不会改成人工禁用或冷却。
7. 未开启探针自动恢复的 `auto_disabled` 渠道只能人工恢复。人工恢复清零全部自动运行态并递增健康版本，但不会把 `admin_state=disabled` 改为启用。

探针失败继续使用独立计数：健康渠道的定时探针连续失败达到探针阈值时，可以按渠道互斥失败动作进入冷却或自动禁用；未达阈值只记录探针告警，不增加业务连续失败数。冷却/半开验证探针失败按半开规则重新冷却；自动禁用恢复探针失败只清零恢复成功数。渠道满载导致探针未获 lease 时记录 `probe_skipped_busy`，不视为探针失败。

**请求日志、运行日志和页面解释**

Attempt 继续只表示一次实际上游调用，不用虚假的 Attempt 表示跳过。SQLite 增加轻量 `request_route_events`，至少保存请求 ID、顺序、事件类型、当前渠道、关联渠道、原因、受控详情和发生时间。事件类型固定覆盖：

- `candidate_skipped`：记录 `concurrency_full`、`cooldown`、`auto_disabled`、`admin_disabled`、`half_open_claimed` 等原因。
- `channel_switched`：记录失败渠道、目标渠道和触发错误类别。
- `health_changed`：记录失败计数前后值、健康状态前后值、健康版本和冷却截止时间。
- `routing_exhausted`：记录全部满载、全部不可用、实际尝试预算耗尽或候选耗尽。

一次 Attempt 的终态、健康变化和紧随其后的路由事件应尽量在同一 SQLite 事务中落库；无法写入持久账本时停止继续重放并返回本地账本错误。运行日志同步发送对应结构化事件，必须携带 `requestID`，有实际调用时同时携带 `attemptID`。操作日志只记录渠道配置变更、人工恢复、人工启停等管理动作；自动跳过、切换和健康转换只进入请求日志与运行日志，避免把系统路由事件伪装成人工操作。

请求详情把 Attempt 和路由事件按时间/顺序合并为时间线，至少能直接读出：

```text
A 调用失败（http_503）
A 连续失败 1 -> 2，degraded -> cooldown，冷却至 ...
A -> B（跨渠道重试）
B 因并发 8/8 跳过
A -> C（跳过 B 后继续）
C 调用成功
```

请求列表不再显示“同渠道重试次数”。改为展示实际 Attempt 数、跨渠道切换数和最终渠道；`channelChain` 只包含实际调用过的渠道，跳过记录只在详情时间线显示。渠道列表和目录接口增加进程内 `inFlight / concurrencyLimit` 快照用于观察，不把该快照持久化或迁移。

**渠道编辑与全局设置交互**

渠道编辑“请求设置”最终只展示：优先级、并发上限、请求超时、流式空闲超时、连续失败阈值、失败后动作和冷却基数。“失败后动作”选中自动禁用时，冷却基数禁用并说明不会使用；选中冷却时恢复可编辑。失败动作始终是单选，不增加两个独立开关。

“探针设置”把两个开关明确标为“启用探针”和“探针自动恢复”。开启自动恢复时自动要求探针启用；关闭探针时同步关闭自动恢复。自动禁用但未开启探针自动恢复是合法配置，页面提示“达到阈值后需要人工恢复”。“人工恢复”与“立即探测”保持两个独立操作；人工恢复必须二次确认并说明不会启用人工禁用渠道。

设置页新增“请求策略”区域，展示现有连接、首字节、默认流空闲和逻辑请求总超时，并新增“最大渠道尝试数”。这些设置对新请求即时生效；监听地址仍按现有规则重启生效。阶段 13 起，Request 固定取得同代全局执行设置；reasoning/service-tier 等全局渠道设置提交时，只为合成后的有效执行配置实际变化的渠道递增配置/健康代次，旧 Request 继续使用旧设置且健康归因保持中性。页面不增加排队或同渠道重试配置。

“最大渠道尝试数”旁必须说明：`0` 表示尝试全部合格渠道，`1` 表示只调用首个可准入渠道，`2` 表示首个渠道失败后最多再调用一个不同渠道。该值不是每个渠道的重试次数。

所有新增前端方法继续使用规范中文注释；样式只沿用现有 flex/普通块布局，不使用 `grid` 或 `gap`。

**数据库与配置替换**

- SQLite schema 由 v21 升到 v22，新增 `request_route_events` 及请求顺序索引；升级事务通过重建 `channels` 表删除 `retry_count`，保留其余渠道数据与引用关系，并在提交前执行外键完整性检查。

**模块边界**

- `RuntimeCoordinator` 封装不可变认证/运行快照、同代全局执行设置与 `PricingSnapshot`、代理 `RequestLease`、system/admin/content `OperationLease`、管理读复核、维护状态和短提交窗口，但其能力全集不得形成一个供所有调用方依赖的大型 interface。构造时按消费者交付 `ProxyAdmission`、`AdminRead`、`AdminChannelOperations`、`ConfigReplacementCommitter`、`RecoveryCommitter`、maintenance 等窄 façade；`server` 看不到通用 short/draining runner，`configreplace` 与 `RecoveryPointStore` 也只能看到各自的类型化 committer。coordinator implementation 可复用内部 short/draining executor，但外部 command/capability 不得携带任意 SQL 或 `func(tx)` callback；只有存在生产/测试两种真实 adapter 时才建立 interface，不为 mock 暴露内部 seam。入口先无 lease fallback。`runtimeResponseWriter`、`auditResponseWriter` 及后续 wrapper 必须保持 `Unwrap() http.ResponseWriter` 链，真实连接读取 deadline 的设置或清除失败都在建账本、写数据库/secret 或开始上游流之前 fail-closed、返回 500 并关闭连接。管理渠道长操作以 - `Snapshotter` 只使用不进入业务连接池的独立只读单连接：开始只读事务后必须执行真实读取以固定源快照，再从同一连接分页执行 modernc online backup（每步最多 256 页）。业务连接在 Step 间持续提交不得使 backup 重启；瞬时 BUSY/LOCKED 在总 deadline 内重试。成功顺序为固定快照 → Step → `Finish` → 结束事务 → fsync，取消、持续 BUSY/LOCKED、其它错误或超时也必须 `Finish` 并回滚事务、关闭连接。固定 `snapshotBackupTimeout=120s` 从打开事务前开始，覆盖真实读取、全部 Step、`Finish` 和事务释放；超时只中止本次恢复点 capture 并走 artifact abort，以限制 WAL 保留，本阶段不增加 UI 配置。
- `SecretStore` 把逻辑 ref 映射到带 generation 的不可变物理账户；authority v2 journal 用 `put_prepared` / `put_committed` / `delete_pending` 原子切换 active generation。keyring 写入结果不确定时必须把原 candidate 精确登记为 `abandoned_candidate` 再切新的 local generation；旧 generation 被 lease pin 时连续 G2/G3 Put 继承并追加完整 retired 集合，不等待旧 pin、不覆盖清理证据。每 ref 最多 64 个 retired slot，新 Put 预留最坏 2 项空间，不足即 409 且零变化。启动必须在 `storage.Open` 和任何业务 secret 读取前执行 `RecoverPendingAuthority`，物理写后崩溃不得丢失旧 active 或未决 candidate。
- 本地 fallback 的物理持久化必须先于 authority 提交：`master.key` 仅在确认没有既有本地密文依赖时原子初始化，读取不创建密钥；candidate 密文经私有临时文件、文件 fsync、原子发布和父目录同步后才允许发布 `put_committed`；删除密文并同步父目录后才移除 authority 清理证据。已有本地账户依赖而主密钥缺失/损坏时 fail-closed，不生成替代密钥。A2 同时验收主密钥初始化、candidate 发布和删除各持久化窗口，细则见详细规格 3.0 的本地后端契约。
- `SecretRefLifecycle` 管理数据库业务 ref 的 provisional/retired 持久账本。新 ref 必须先登记再 Put，并在业务 COMMIT 中移除 provisional；旧 ref 同事务进入 retired。物理删除按 ref 检查所有仍引用它的活跃 snapshot、当前数据库、`SecretReadLease` 与资源 pin，不能只等待紧邻上一代；固定令牌、restore、恢复点 bundle key 和正文资源继续由各自 journal 管理。`database_committed` 不进入该 JSON 账本。
- `ContentResourceStore` 在正文模块内管理文件、`content_blobs` 行和 key ref 的 creating/deleting journal。首次 `Store.Put` 或文件写入前先原子登记 `{operationId,requestId,blobId,keyRef,stagedPath,finalPath}`；每个 blob 同时只有一个由该深模块签发的 resource-operation capability，Create、容量/保留期/手动清理、读取、capture 和恢复共用这一 seam。creating 以精确业务行（含 requestId）作为唯一提交证据，有匹配行就要求已提交资源完整并只前滚收口，无行则幂等清理未提交文件与 secret；创建 COMMIT 后也必须先由匹配 kind+operationId 条件清除 creating，删除才能发布自己的新 opId，迟到创建收尾不得删掉 deleting。deleting journal 一经 fsync 就是删除意图的持久证据：恢复先校验仍存在的行与 journal 身份，再继续幂等删除文件、精确行和 key，最终也只条件清除自己的 owner；删除中资源已不存在是合法中间态，不能套用 creating 的完整性规则。已有 deleting owner 时新正文查看返回 `content_unavailable` 且不建 pin；已有 read pin 则删除等待。字段不符、路径越界、owner 不符、仍有 pin 或精确身份冲突均 fail-closed。独立定时/手动日志清理在整个“正文→父 Request”流程持有 maintenance operation lease；正文写入内部的容量 trim 则继承仍有效的父 RequestLease，不重新申请顶层 maintenance lease，draining 仍允许该在途请求完成。父 lease 必须覆盖同步 trim、正文写入及 journal 收口，不允许清理回调逃逸到父 lease 释放之后；trim 仍遵守同一资源 owner、pin/fence 和删除 journal，只整理正文容量，不删除父 Request、审计或运行日志；父行在 pin/fence 登记的同一序列点、同一短 SQLite 事务内复核终态、保留期、活跃引用、正文行及按 requestId 重建的未完成 journal 后条件删除，正文因 pin 被跳过则父行也必须保留，不得通过外键级联绕过。恢复 drain 等待整段清理及正文执行者后，必须在旧 live 尚未移动时调用同一恢复入口并确认 journal 为空，才允许进入 switching；staging 崩溃则先终止未提交 restore，再按当前旧库分 kind 收口正文 journal。该本机 journal 不进入配置、迁移包或恢复点，也不扩张通用 `SecretRefLifecycle` 接口。
- 每小时 `runStorageMaintenanceScheduler → maintainHotStorage`（含启动时立即执行的一轮）复用 coordinator 的 maintenance operation：在读取设置或枚举小时桶前取得 lease，覆盖 `AggregateMissingMetrics` 的全部读取、计算、聚合提交和 `TrimProbeRuns`，最后一次操作返回后才释放。draining 拒绝新任务并等待已有任务或按 30 秒超时零恢复提交退出；dirty revision 只解决同一集合内的统计更新，不充当恢复集合代次。具体接线与交错 gate 见详细规格 3.1 / A4。
- 管理运行日志 SSE 走 `RuntimeCoordinator.BeginAdminRuntimeStream` 当前令牌代次复核并登记可取消订阅，不把无限流当作一次性 `CaptureAdminRead` 或全生命周期 `OperationLease`。管理令牌提交换代、导入/恢复发布新令牌或进入 draining 时在同一序列点取消旧订阅；此后不选取新的历史/live 日志帧或 reset，换代前已有发送许可的单帧可写完。订阅写入有逐次期限且不跨写持全局锁，断开时释放资源；新订阅在维护中 503，前端使用当前令牌和现有游标重连，401 等待令牌更改，503 遵循 `Retry-After`。

- schema 28 为每个渠道增加服务端生成、更新时不可变且全库唯一的 `channel_identity`、从 1 开始的 `channel_config_version`，以及显式 `stream_idle_timeout_mode=inherit|override`；前者识别删除重建后的 incarnation，后者识别同一 incarnation 内的实际上游执行/健康归因语义，现有 - `PrepareAttempt` 封装**已保存渠道**的候选预检查、渠道凭证读取、准入 reservation、渠道敏感词和半开/并发 `AttemptLease`。业务、自动探针与 saved admin operation 分别使用 Request/system/admin snapshot；动态准入必须按 `(channel_id, channel_identity, channel_config_version)` 复核当前行。无行或 identity 不同跳过为 `channel_removed`。identity 相同但 config version 不同时，automatic/manual probe 跳过为 `channel_config_changed`；旧业务 snapshot 仍复核当前人工状态、额度、并发，仅在当前健康为 healthy/degraded 时可沿用旧 Base URL/凭证/模型/全局执行设置完成 Attempt，计费照常但健康归因固定 `stale_config_neutral`，不得领取当前配置半开 owner或修改其健康；admin discovery 可完成一致旧 snapshot 但同样不结算健康。config version 相同才进入当前状态机。purpose 契约固定为：manual probe 保留版本化探针健康结算，half-open 成功转 healthy、失败转 cooldown，healthy/degraded 失败累计探针失败，但不自动恢复 `auto_disabled`；automatic probe 才可按 probe enabled、autoRecover 和阈值恢复 `auto_disabled`；admin discovery 不结算健康；draft channel 不进入持久健康/额度/Attempt 状态机。所有非业务 purpose 均不计费、不累加 used、不清额度门闩，也不启用人工禁用渠道。schema 28 的半开占用同时保存至少 128 bit 高熵 `half_open_claim_owner`；领取、正常结算、not-sent、过滤取消和兜底释放都必须匹配 `channel_identity + channel_config_version + health_version + owner`。若 Prepare 后配置再变化，Attempt/计费继续完成，健康部分 CAS 失败后 no-op 且不能清新 owner。只有原子取得可承接 reservation 的业务候选才执行自己的词表，命中时 owner-aware 释放 reservation 并整次返回 400，不 fallback、本候选不建 Attempt；此前完成的 Attempt 不回滚。成功返回的 lease 已携带精确代次凭证，调用方不得再按 `secret_ref` 二次读取。reservation 在 `AttemptLease.RecordAttempt` 提交 processing Attempt 前阻止删除该 identity，COMMIT 后由历史引用接管；调用方不得绕过 lease 直接插入 Attempt。未保存新渠道或尚未提交的编辑表单必须走 draft admin operation，不进入本模块。

- `ContentFilterEngine` 在不可变运行快照发布前编译多 owner Aho-Corasick 和 owner 倒排索引，正文只规范化和扫描一次；只跳过协议合法图片内容块中明确的图片 data URL 或 Anthropic base64 source.data，普通 text/input/system/tool 参数不因长度、字符集、可解码性或 data URL 前缀而跳过，具体字段白名单按详细规格 0.8。Evaluation 只保存 matched pattern，不按共享词展开全部 owner。单请求 8 MiB、每 64 KiB 取消检查，快照最多 10,000 个模式/1 MiB 模式字节及 100,000 owner-pattern 关联/4 MiB owner 索引。每个 Request 固定取得一个同代 `PricingSnapshot`；该 Request 的初始与全部 fallback Attempt 都只从它解析各自价格，并在 processing Attempt INSERT、发上游前持久化匹配结果。目录改价只影响之后取得新 RuntimeSnapshot 的 Request，结算不得查询 live 目录。计价状态唯一顺序为：usage missing/invalid/协议未知 → `usage_unknown`；usage valid 但目录无价/歧义/非 USD/未知单位/当前模型无法表达 → `unpriced`；只有 usage 与价格都可计时才按列表密钥/通用令牌区分 `priced` / `admin`。通用令牌不得覆盖 unknown/unpriced。Anthropic 正数 cache creation 可能同时含 5m/1h 写入；当前单一 cache-write 价格不能唯一表达 TTL，统一按 usage valid + unpriced + 零收费降级，不能部分计价。模型价格前端编辑、提交、重新打开和范围比较与后端相同，以规范十进制字符串为权威；空字符串是缺价，显式 `"0"` 才是免费。
- `RecoveryPointStore` 统一同实例恢复点的 `Create/List/Verify/Restore/Delete` 生命周期，并把 restore sidecar 的 `RecoverPendingBeforeRuntime` 与恢复点自身 `.creating-*` / deletion artifact 的 `RecoverArtifactJournals` 分成两个顺序明确的内部入口。恢复点只支持在 namespace、SQLite binding、authority 和规范化真实路径均未变化的原路径绑定实例内回滚；跨机器同路径复制不受支持但不保证检测。创建和删除均使用持久 journal。`Create` 立即 `defer` capture 的幂等关闭；capture 先在正文资源 seam 关闭新删除并有界等待已经取得 owner 的 deleting predecessor，只有 ready 才调用 `Snapshotter` online backup，从产物收集 refs 并 Seal 精确 pin。先行删除已经删文件但尚有业务行时不得开始 backup；等待超时返回可重试 409 且不发布恢复点。正文复制和 bundle 加密在 coordinator 外执行，artifact 原子发布或 abort 状态落盘后才释放 capture。Restore 永远只读原 committed SQLite artifact/manifest/bundle，在 opId 专属工作副本中改写 ref；sidecar 在任何 staged `Store.Put` 前一次性持久化按 channel id+identity、proxy key id、content blob id 定位的规范 `secretBindings(sourceRef→stagedRef)`，并记录工作副本 path/state/sha256。切库和 committed 重入都逐 owner 验证当前 stagedRef 的明文等于 bundle 对应 sourceRef，不能仅检查 ref 集合可读；交换两个 owner 的 stagedRef 必须失败。在线恢复 sidecar 的 `committed` 表示仍在 draining 中完成恢复点 manifest、新 secret/ref、`CloseInterruptedWork` 和运行快照的最终化；冷启动遇到 committed 时，`RecoverPendingBeforeRuntime` 只验证/补齐持久集合并返回 storage-owned、无公开构造器的单次 `PendingRestoreStartupFinalization`。随后唯一启动清单完成账本收口和初始 snapshot 发布，coordinator 验证自己的 opaque receipt 后，通过只含 capability 与已验证 digest/generation 的窄 storage 接口完成复核，才原子进入 `cleanup_pending`；此后显式调用 `RecoverArtifactJournals` 收口恢复点创建/删除 artifact，不能把它遗漏在模糊的 `RecoverPending` 中，也不形成 storage→coordinator 包依赖。artifact 的逻辑状态、身份或持久接管失败阻止监听，已由 journal 接管的物理删除可后台重试。**恢复 finalization 前不得物理清理恢复集合中的 tombstone 密钥；`CleanupTombstonedKeys` 只在成功进入 `cleanup_pending` 后运行，数据库/引用/账本失败闭锁，已接管的物理删除才后台重试。**工作副本必须在进入 cleanup_pending 前由 sidecar 精确删除并 fsync；进入 cleanup_pending 后恢复语义结束且 live 可以正常演进，sidecar 只负责精确 `oldContentDir` 垃圾清理，不再用旧 binding/manifest/fixed secret/ref/configDigest 校验当前 live、重放恢复或回滚后续业务状态。旧目录删除和父目录 fsync 成功前保留 sidecar 与 SQLite marker，`cleanup_pending` 时普通请求、配置导入和令牌修改可继续但下一次 Restore 返回 409；后台和启动只按 opId 与专用根路径幂等续删，完成后才依次删除 marker、sidecar。配置替换必须在 coordinator 提交序列点读取并保留当时仍有效的 marker，不能使用 prepare 缓存复活已删除 marker；冷启动因已持实例锁且无监听器/后台任务，可用启动独占短事务条件删除相等 marker，不得伪造 coordinator。
- 恢复点 SQLite 在 `.creating-*` 内完成净化事务后、发布 committed 前必须封存为独立单文件：仅对暂存副本完成所需 WAL checkpoint，收敛到 `journal_mode=DELETE`、`synchronous=FULL`，关闭全部连接，验证文件头和无 `-wal/-shm/-journal` 依赖，再 fsync 文件及父目录；其后才计算最终大小/sha256、写 manifest 并发布。`RecoveryPointStore` 统一通过受控只读入口读取封存 artifact（`mode=ro&immutable=1`，先核对封存状态、文件头、大小/hash 及不存在 sidecar），Create 的最终领域校验、Verify 和 Restore 均不得修改原 artifact 或产生旁路文件；immutable 绝不能用于 live/preflight 或未封存 WAL 副本。creating journal 在首次写入前登记 SQLite 及其确定的旁路路径，同一 owner 负责 abort/崩溃清理；不能用删除尚需回放的 WAL 冒充封存。已发布 artifact 不就地修复，异常由 Verify/Restore 拒绝；Delete 的 journal 精确接管同 backupId 的旁路路径。固定源读事务、120 秒源备份 deadline 和 capture/Seal pin 顺序保持不变。
- `ValidateRestorableSnapshot` 把引用分为当前结构关系、历史请求快照和 processing 主体三类。渠道成员、当前列表密钥所属组、正文所属 Request 及其它 schema 28 当前外键必须存在；终态 Request 的 `proxy_key_id/name` 和所有 Request 的 `access_group_id/name` 只是鉴权历史快照，原对象删除后可悬空，恢复不得补建对象。processing Request 的非空 key id 必须仍有对应密钥行（允许 tombstone），缺行在 live 切换前拒绝；processing 的访问组快照仍可悬空，先由 `CloseInterruptedWork` 收口，再允许 tombstone 清理。
- `cleanup_pending` 的 `oldContentDir` 由 `RecoveryPointStore` 内部唯一清理流程负责，在线、后台重试和冷启动不得各自复制顺序：精确路径校验 → 删除成功或 not-found → fsync 父目录 → 原子写 `oldContentCleanup=done` 并 fsync sidecar → 条件删除相等 marker → 删除 sidecar 并 fsync。任何入口都不得从 pending 直接删 marker；冷启动只因持有实例锁且未启动监听，可用启动独占短事务完成 marker 条件删除。
- `storage.CloseInterruptedWork` 在更新前收集“原 processing Request”与“本次关闭的 processing Attempt 所属父 Request”两个集合，单事务把 processing Attempt 收口为 `failed/process_interrupted`、中断 Attempt `usage_unknown + 零收费 + health_attribution=not_applied`，并对两个集合的并集重算 attempt_count/金额/计费状态。只有原 processing Request 改成 `error/process_interrupted`；父行若已是 success/error/partial 等终态，则保留其原 final_status、completed_at、响应/HTTP/错误结果，只修正 Attempt 派生聚合。已计费 Attempt 金额保留，不再次增减额度。函数还只在确认旧执行者已不存在时把失主 `health_runtime.half_open_claimed=0` 与 `half_open_claim_owner=''` 一并清除；普通请求结算与释放必须 owner-aware，不得调用该无 owner 批量路径。不处罚健康、不重置失败计数、不改额度、不 fallback。所有实际变更的 Request/Attempt 先按关联请求的 `started_at` 收集 UTC 小时并去重，再在同一事务用现有 `markHourlyMetricDirtyTx` 标脏；重复执行无状态变化不得增加 dirty revision。它在唯一权威启动清单中先于监听/探针执行；在线同实例恢复时在 drain 和新库/固定 secret 校验之后、发布新运行快照及开放请求之前对**恢复后的库**复用，失败 fail-closed；不能只依赖旧 `server.Run` 的启动清理。
- 导入/恢复的浏览器令牌 handoff 统一使用共享 `PendingAuthTokenHandoffV1` 和唯一严格编解码入口，wire 固定为 `{"version":1,"opId":"…","adminToken":"…","proxyToken":"…"}`。缺少或未知 version、未知字段和错误类型都拒绝使用并进入重新输入令牌流程，禁止回退到无 version JSON 或裸字符串。
- 列表密钥 tombstone 延迟物理清理同时等待该密钥全部 `RequestLease`、`requests.final_status='processing'` 和关联 `attempts.status='processing'` 消失；请求字段是 `final_status`，不存在 `requests.status`。只有 processing Request、尚无 Attempt 时也不能清理密钥行。
- 不可变认证索引只快速校验 token 并解析列表密钥 id，不缓存最终 quota 准入结论。`BeginProxyRequest` 在 coordinator 短提交序列点内按 key id 从 SQLite 复核 tombstone、token hash、人工状态、group 与当前 used/limit，并在同一步登记 `RequestLease`；其成功读取是主体准入线性化点。Attempt 结算先 COMMIT 则紧邻请求必须 403，Begin 先读取则该请求属于允许继续结算的在途请求；稳定 `RuntimeConfigProjection` 继续排除这些动态字段。
- `CaptureAdminRead` / `CaptureAdminSecretRead` 在当前管理令牌复核的提交序列点，通过同一次短 SQLite 只读事务捕获管理列表/摘要/配置及迁移导出的稳定配置和 used/limit/status/reason/quota 门闩；与已发布配置代次一致，secret ref 的精确 generation 在事务结束前 pin，明文复制、加密及网络 I/O 在事务外。并发结算只允许导出完整前态或完整后态，动态字段继续不进 `configDigest`。
- OpenAI Responses/Chat SSE 的协议允许顶层 `usage:null` 视为尚未提供用量（missing），后续合法最终 usage 可计费；非法非空容器、非法明细/数值仍为粘性 invalid。若最终始终无有效 usage，则 `usage_unknown + 0`。
- 恢复点 prepare 若遇无正文引用的实例尚无 `liveContentDir`，必须先持久创建空 live 及其父目录，再发布 staging sidecar；有正文引用却缺目录拒绝。sidecar 落盘后中断可按 staging 安全收口，不放宽有损坏数据时 live 缺失即拒绝的规则。
- 列表密钥删除使用 tombstone 和延迟物理清理：新鉴权与管理列表立即不可见，已有 Request/Attempt 仍能按原主体结算，最后一个引用释放后再删除行和 secret。普通 CRUD、固定令牌修改和密钥删除不得触发全站 drain。
- 裸 `Lock/RLock/Unlock`、锁顺序、“调用方已持锁”和 `...Locked` helper 不得成为跨模块接口；调用方只使用上述语义化 operation/lease。

**内部工作包与 gate**

阶段 13 使用 A–E 五个不可独立发布的内部工作包；schema 28 只在 A 的空数据目录初始化中创建一次：

1. **13A 基础能力**：只读记录当前格式/hooks/EOF whitespace blocker，不自动修改无关 dirty 资产；按「全新 schema 28 DDL/实例身份 → authority v2 SecretStore → lifecycle/provisioning/固定令牌 journal → RuntimeCoordinator/中断收口 → ContentResourceStore/独立 Snapshotter/恢复点内核」五个内部检查点推进，每点交付自身最小反馈环和失败/崩溃验收后再进入下一个，不新增发布批次或协调层。A 首点必须把文档全部新建表、索引、default 插入和关键约束在临时 SQLite 中实际执行；仅检查 SQL 字符串存在不算通过。13A 仍覆盖正文 creating/deleting 两套崩溃恢复分支及 kind+operationId owner 交接、read/delete/capture 统一资源准入、父 Request 条件清理及整段 maintenance lease、管理运行日志代次订阅与取消、连续 Put/不确定 candidate 启动恢复、共享稳定 RuntimeConfigProjection/启动前滚、含 PricingSnapshot 的运行快照、HTTP 读取时限，以及 restore 的只读源 artifact、opId 工作副本、owner-aware `secretBindings`、pre-runtime/finalization 与恢复点 artifact journal 收口显式装进唯一启动清单的无 UI `RecoveryPointStore`；两个既有 ResponseWriter wrapper 必须补齐 `Unwrap()`，读取 helper 对 deadline 设置和清除错误统一 fail-closed。既有 blocker 需要时另立用户明确授权的 baseline maintenance batch。
2. **13B 主体与选路**：访问组、以至少 128 bit 服务端随机且不可复用 id 作为主体 identity 的列表密钥、包含 6 位随机部分的 prefix、`RouteScope`、tombstone、物理删除同事务 affinity 清理、带 `channel_identity + channel_config_version + stream_idle_timeout_mode` 且冻结全局执行设置/有效超时的固定目录快照，以及业务/自动探针/saved admin operation 共用的 `PrepareAttempt` 代次凭证/reservation 基础；管理渠道操作另以 `saved_channel|draft_channel` 类型化，未保存新渠道和未提交编辑值使用 owned 表单凭证与 admin operation lease，不进入持久渠道准入或账本。共享的有效 `ChannelExecutionProjectionV1(channel, globalChannelSettings, requestPolicy, familyModelMappings)`、全局 reasoning/service-tier 与影响渠道健康的 RequestPolicy 设置同事务选择性增版、显式 inherit/override 流空闲语义、全局模型映射同事务按协议族保守增版、旧配置健康中性分支、manual/automatic/admin discovery 的显式健康矩阵、半开 reservation 的 identity/config/health/owner 条件领取/释放、密钥和渠道 limit 修改、reset usage、quota 状态重算及 safe 占位密钥状态规则都在 B 闭环，但不实现真实 Attempt usage 计价或自动 used 累加。渠道复制按是否有凭证选择 provisioning 或普通类型化短提交。普通持久写只允许 `POST /channels/bundle` 新建和 `PUT /channels/{id}/bundle` 更新；新建拒绝 body id、更新只认路径 id，行级 POST/PUT 固定拒绝，前端不提交 id/identity/config version。所有渠道创建/复制/导入/恢复入口遵守内部 identity/version 的生成、保留与禁止外部注入规则，`AttemptLease.RecordAttempt` 关闭 Prepare 成功到 processing Attempt COMMIT 之间的删除窗口。`configreplace` 负责 owned batch 导入并复用普通渠道凭证领域校验：safe 导入全部停用、complete/migration 启用渠道必须带有效凭证且不得静默停用，完整导出缺凭证时整体 409。管理 UI、配置 schema 9 和迁移包 v2 同时完整往返 idle mode。
3. **13C 计费与额度**：usage 三态（OpenAI SSE 顶层 `usage:null` 为 missing，非空非法数据粘性 invalid）、同一 Request 固定价格目录且各 Attempt INSERT 持久化匹配结果、精确十进制计价、Attempt 幂等结算、密钥/渠道 used 自动累加、quota 门闩和详情展示；状态严格按 usage→价格→主体判定，通用令牌的合法 usage + 无价仍为 `unpriced`，不是 `usage_unknown` 或 `admin`。Anthropic 正数 cache creation 因单一价格无法表达 5m/1h TTL，明确降级为 usage valid + unpriced + 零收费。模型价格编辑器、前端类型、提交、重新编辑和范围比较全链路保持规范十进制字符串，空值与零价不混用。复用 B 已完成的额度管理接口，不重复归属 limit/reset。额度是目录价格推算的软限制，允许在途超额且无 usage/无价时不扣费，不能宣称为严格上游支出上限。
4. **13D 内容拦截**：编译式多 owner matcher/倒排索引、单次正文规范化/扫描、模式与 owner-association 容量及取消预算、全局词表，并把渠道词表接入 B 已建立的 `PrepareAttempt` reservation，补齐结构化账本；fallback 后候选命中只拦截后续尝试，不撤销此前 Attempt 的计费和健康结算，过滤取消只能释放自己的半开 owner。
5. **13E 同实例恢复与发布**：在 A 的恢复点内核上接入列表/删除/显式恢复 API 与 UI，完成 online backup/精确 pin/恢复的全量崩溃与并发矩阵；在线 `committed` 在 draining 内发布 snapshot，冷启动 committed 由 pre-runtime capability 等待初始 snapshot receipt，两者完成恢复最终化后才进入 `cleanup_pending`。恢复集合中的 tombstone 密钥在 finalization 前不得物理清理，成功转相位后再幂等清理并允许后台重试。cleanup_pending 只持久接管旧正文目录到删除及 fsync 完成，不再用旧恢复清单约束已正常演进的新集合，但阻止下一次 Restore；最后完成响应式 UI 以及 Windows、macOS、Linux 验收。

13A 的首个 gate 必须在临时 SQLite 实际运行完整 schema 28 新表/索引 DDL、插入 default，并验证唯一默认组、未物化密钥禁用、正 `channel_config_version`、`stream_idle_timeout_mode` 枚举、override 正数约束、Attempt `health_attribution` 枚举及 `half_open_claimed/owner` 一致性等关键约束；之后各检查点依次验证 authority 各崩溃点、keyring 物理写成功但返回错误、G1 pin 下连续 G2/G3 Put、processing 账本及失主半开占用的同事务幂等收口（Attempt 用 `failed`、`health_attribution=not_applied`，原 processing Request 用 `error`，已终态父 Request 只修正 Attempt 派生聚合，同时清 claim/owner，同事务按请求开始小时去重标脏，重复执行不加 revision）、committed batch 在 COMMIT 后立即崩溃/返回不确定/Complete 前崩溃时的摘要校验与启动幂等前滚。正文 creating 必须覆盖“secret 已写但无业务行”“final 文件已发布但无业务行”“业务行已提交但 journal 未删”；暂停在最后一个窗口并发触发容量、保留期和手动清理，deleting 不得覆盖 creating，创建者迟到收尾不得删除后续 operationId 的 deleting。deleting 必须覆盖 journal 刚发布、文件已删、行已删、key 已删与 journal 删除前各中断点，连续重启只前滚同一 owner 的删除意图，not-found 幂等成功且仍有 pin 时不删除。恢复点 `.creating-*` / deletion artifact 逐步中断后，唯一启动清单必须在 restore finalization 后显式调用 `RecoverArtifactJournals`；逻辑状态/身份/持久接管失败阻止监听，已接管物理清理允许后台重试。restore staging 期间并发正文操作后进入 drain，必须等待执行者并在切目录前把 journal 收敛为空。A 只能用明确标注的受控 SQLite 短事务改动态字段，证明它们不进入 `configDigest`，不得提前调用或宣称完成 C 的真实 Attempt 计费。还包括大库 online backup 期间代理/Attempt 结算持续成功、“删除先取得 owner 且文件已删/行尚在时开始 capture”必须有界等待或可重试失败且不得启动 backup，以及“恢复点仍在 capture 时发起 restore”：restore 等待该 operation lease；30 秒内未释放则退出 draining、保持零提交并恢复接流，宽 fence 收窄为精确 pin 前后不得漏资源或永久 pin。实例 identity gate 只承诺拒绝不同规范化真实路径；跨机器相同绝对路径复制不受支持但当前不保证检测。HTTP 读取期限反馈环必须穿过真实 `runtimeResponseWriter → auditResponseWriter → handler` 链，覆盖设置/清除成功、两者各自失败、慢 body 和清零后 SSE/keep-alive，不得以裸 handler 代替。结构搜索还必须证明 `server` 没有通用 short/draining callback runner，`configreplace` 与 `RecoveryPointStore` 只依赖各自 typed committer，所有其它消费者只得到自己的窄 façade。

13A 的 A5 必须验证净化事务确实进入最终 SQLite 主文件；在 checkpoint、DELETE 模式收敛、连接关闭、fsync 和 committed 发布前分别注入失败，未封存产物不得可见，abort/重启清理不得遗留该 backupId 的旁路文件。最终大小/hash 只取封存后文件，连续 Verify/Restore 前后原 artifact 文件集合与 hash 均不变。

13A 的 restore staging 还必须证明原 committed 恢复点 SQLite/manifest/bundle 全程只读，全部 `secretBindings` 在任一 staged Put 前一次性 fsync；在 binding 发布、部分 Put、部分工作副本改写和 ready 发布前分别崩溃，连续启动只清本 opId staged ref/工作副本。工作副本只在 path/state/sha256 完整且三表逐 owner 反向核对通过时 ready，原 artifact 哈希始终不变。

13A 还必须验证自动/手动清理在正文被 read/capture pin 跳过时保留父 Request 和正文行；processing 请求或未完成 creating/deleting journal 不会被条件删除，释放 pin 并收口 journal 后可重试。正文查看在 deleting owner 已成立时返回 `content_unavailable` 且不建 pin，已有 read pin 时删除只能等待。固定在正文阶段结束、父行删除前发起 restore：draining 等整个 maintenance lease 或超时零提交，绝不在新集合执行旧父行删除。真实管理中间件上的运行日志 stream 与令牌换代竞争时只能建立新代次订阅或 401；旧连接换代后不能选取新日志。长 SSE 打开时导入/恢复必须可进入 draining 并取消订阅而不等待它；慢客户端不持全局锁，前端 401/503 的重连分别等令牌变化/按 `Retry-After`。

13B 还必须覆盖 safe/complete/migration 同 id 替换：目标原渠道分别处于 auto_disabled、cooldown、half_open（含 owner）并有非零失败/探针计数和历史记录，导入新 URL/凭证或 safe 无凭证配置后，新 identity/config version=1 与全部健康初值同事务生效，历史记录保持不变；safe 仍人工停用，额度按导入值派生，不因健康初始化解除。事务失败完整保留旧身份与健康行；不在包内的日志占位保留原健康字段；同实例恢复只清失主 claim 而不做此初始化。

13B 必须证明 owned batch 不等待自己但等待其它 operation，并证明 COMMIT 后 snapshot 发布失败不会 destructive Abort，导出/恢复点也不会携带 committed journal；safe 占位密钥经额度重置、提高限额或改不限额仍保持 disabled，轮换后也不自动启用；无凭证 disabled 渠道复制只走普通类型化短提交、有凭证复制仍走独立 provisional。列表密钥 K1 建立 affinity 后 tombstone 并物理清理，再创建 K2：普通 POST 带 id 必须 400，K2 的随机 id 不得复用 K1，K1 affinity 必须与行删除同事务清空，K2 猜中旧 `previous_response_id` 也不能命中；complete/migration 只有先清空全部 affinity 才能重用包内逻辑 id。同一组内也必须按新主体隔离，不能只依赖 RouteScope。未保存新渠道必须能测试/发现模型，编辑已有渠道但尚未保存时必须使用未提交的新值；管理令牌在 draft lease 前轮换则 401 且零上游请求，lease 后进入 draining 则等待或超时零提交，草稿操作不得产生任何持久渠道/Attempt/secret 状态。safe 普通渠道导入停用且显示缺凭证，complete/migration 对启用渠道缺凭证拒绝而非静默停用，完整导出缺可读凭证 409。B 用受控 SQLite 短事务把一致状态从 `used=90,enabled` 切到 `used=110,disabled/quota_exhausted`，只验证管理列表/导出的一致读取，不得记为真实结算；真实 Attempt 跨限归 C。密钥清理必须使用真实的 `requests.final_status` 字段，不能在只有 processing Request、尚无 Attempt 时物理删除。还必须固定验证「旧 snapshot 的 `(channel-001, identity-A)` → 删除 A → 自动编号或复制创建 `(channel-001, identity-B)` → 恢复旧请求」只会跳过旧渠道，不能调用旧上游或向 B 记账；Prepare 成功到 RecordAttempt COMMIT 前并发 DELETE 必须 409，COMMIT 后继续由历史引用拒绝删除。健康代次交错必须覆盖旧 lease `(identity-A,G1,O1)` 迟到结算/释放时新半开验证已领取 `(identity-A,G2,O2)`：旧 lease 不能清 O2，只有 O2 自己结算/释放后才可再次领取。配置代次还必须覆盖两扇渠道 bundle 窗口和两扇全局设置窗口：R 在 Prepare 前持 C1/G1 snapshot 后提交 C2 或 G2，以及 R 已 Prepare 后再提交 C2 或 G2。R 始终使用旧渠道/全局执行配置，不能领取、恢复或释放新配置半开 owner；迟到结算只完成 Attempt/计费并健康 no-op。healthy/degraded 下允许继续的旧 business Attempt 固定 `stale_config_neutral`，half_open/cooldown/auto_disabled 下跳过；新 Request 才使用新配置。共享 projection 还须证明展示/访问/额度字段不误增、上游/健康语义字段必增，固定 reasoning override 和已关闭渠道 service-tier passthrough 不因无效全局变化误增。idle gate 必须证明新渠道默认 inherit；全局 60s→30s 只使 inherit 渠道换代并只影响新 snapshot，override=300s 渠道不换代；inherit↔override 即使当前有效值相同也换代；override+非正数在 bundle/config/migration staging 前拒绝；传输只使用 snapshot effective 值，不再 `<=0` fallback。manual probe 必须覆盖 half_open 成功转 healthy、失败转 cooldown，并证明成功或失败都不自动恢复 `auto_disabled`；automatic probe 只按启用策略和阈值恢复，admin discovery/draft 不产生健康变化，所有非业务 purpose 均不计费、不清额度门闩。

13C 必须用真实可计价 Attempt 把 key `used=90,enabled` 推到 `used=110,disabled/quota_exhausted`，同时验证渠道 used/门闩、账本金额与 `BeginProxyRequest` 当前数据库复核的线性化，紧邻请求不能使用旧 quota snapshot。价格 gate 固定为 Request R 取得 P1 后，A Attempt 期间发布改价 P2，R fallback 的 B Attempt 仍从 P1 解析；改价后新建 Request R2 才使用 P2，所有结算只读 Attempt 行。OpenAI SSE `usage:null → 合法最终 usage` 必须计费，`非法字段 → 合法最终 usage` 仍 unknown。通用代理令牌的合法 usage + 目录无价/价格歧义必须固定 `unpriced/$0` 且渠道 used 不增加，不得写成 `usage_unknown` 或 `admin`；无/非法 usage 固定 unknown，合法 usage + 可计价格才是 admin。Anthropic 分别用 5m、1h、混合和无 TTL 明细对象的正数 cache creation 验证 usage valid 但整单 unpriced/$0，并返回固定原因；已出现的 5m+1h 明细与聚合不相等时必须 invalid，不能仅给其它分量收费。价格编辑器必须让长小数输入→提交→重新编辑不丢精度，清空保持缺价、显式 `"0"` 保持免费，范围比较不经过二进制浮点。

13D 必须证明候选数量不放大正文扫描、共享模式不展开 owner，并覆盖「A 已结算后 fallback 到 B，B 的词表命中」时保留 A 的 Attempt/费用/健康、整次 content_filtered 且不再 fallback；过滤命中、取消和 not-sent 只能释放自己携带的三元组 owner，G1 的迟到释放不得清 G2/O2。

13E 必须在三个目标平台复跑 A5 的恢复点单文件封存与只读打开反馈环，验证净化后的主文件可独立读取、连续 Verify/Restore 不新增 SQLite 旁路文件或改变原 artifact/hash、创建失败不发布、abort/Delete 精确清理旁路文件且不影响其它恢复点或 live。

13E 必须证明恢复点验证在 live 切换前拒绝启用且缺可读凭证的普通渠道，停用无凭证与无凭证日志占位、disabled 的 safe 占位密钥仍可合法恢复；终态请求保留的 proxy key/access group 历史快照允许原对象已经删除且不得触发补建，processing Request 的非空 key id 则必须仍对应可 tombstone 的密钥行。首次无正文目录必须先持久建空 live 再发布 sidecar，sidecar 后立即崩溃可恢复；在线恢复先清失主半开 claim/owner 并标脏恢复后受影响的已聚合小时，再开放请求，健康/失败计数保持不变。新集合在 `committed` 完成验证、收口和快照发布后才进入 `cleanup_pending`；包含 tombstone + processing Request 的恢复点在 finalization 前不得物理删密钥，连续重启后成功转相位才允许清理。冷启动反馈环必须覆盖在线写 committed 后、旧进程 snapshot 发布前崩溃，pre-runtime capability 返回后崩溃，初始 snapshot 构建失败，发布后但 finalization 前崩溃，以及 cleanup_pending 写入后崩溃：前四类始终保留/重建 committed capability 和当前初始 snapshot，最后一类只续垃圾清理；receipt/opId/digest 不符、重复消费或任何 finalization 失败都不得启动监听器。注入旧正文目录删除失败后继续正常产生/清理正文、执行配置导入或令牌修改并重启：启动必须按当前数据库正常通过，只续删精确旧目录，不能再用旧恢复点 manifest/fixed secret/ref/configDigest 校验或重放恢复；配置替换保留提交序列点仍有效的 marker，cleanup 删除后不得被 prepare 缓存复活。分别在物理删除后写 done 前、写 done 后删 marker 前、删 marker 后删 sidecar 前崩溃，均不得误删新的 live/staged/数据根或积累第二个旧目录。恢复点自身 `.creating-*` / deletion artifact 中断必须在 restore finalization 后由唯一清单显式续作，不能遗漏 bundle key 清理或让已删除恢复点重新可见。路径验收只承诺不同规范化真实路径拒绝；跨机器相同绝对路径复制标为不支持但不承诺可检测。浏览器 handoff 的所有写入/启动恢复路径都必须通过同一 `PendingAuthTokenHandoffV1` 严格编解码，缺失/未知 version 必须拒绝。

13E 还必须在数据库 COMMIT 后立即崩溃并连续重启，证明 sidecar binding 足以把 live stagedRef 精确关联到原 bundle sourceRef，不依赖进程内 map；交换任意两个 owner 的 stagedRef 即使二者可读也必须 fail-closed。工作副本在进入 cleanup_pending 前精确删除并 fsync，文件已删但 sidecar 未写 deleted 的窗口可幂等前滚，绝不能修改或清理原恢复点 artifact。

13E 的在线交错还须覆盖恢复开始时日志清理恰好完成正文阶段、尚未开始父行删除：恢复只能等待整段清理结束或超时零提交，不能误删新库同 ID 的 Request。恢复进入 draining 必须立即取消运行日志订阅，换成恢复点令牌代次后旧连接收不到新事件，前端可用当前令牌及游标重新订阅。

每个工作包必须完成自身临时反馈环、文档回填和本地 gate 才能进入下一包。用户只授权单包时，`13A READY` 不自动授权进入 13B；用户明确委派整个阶段 13 时，执行者可在各包本地 gate 通过并记录证据后按 A1→A2→A3→A4→A5→B→C→D→E 连续推进，无需逐包重复请求授权。本地 gate 失败先在当前包修复，不得跳过；待执行的跨平台发布验收单独登记，不当作本地 gate 失败。A–E 全部完成、经单独授权关闭既有 blocker、当前全仓命令门禁全绿、约 1000 行职责拆分以及窄屏与三平台验收全部通过后，阶段 13 才能标记完成或具备发布条件；实际发布仍需用户授权。任何中间构建均不得用于正式数据或正式发布。执行入口、代码落点与交接记录规则见详细规格第 8.0 节。

## 18. 验证策略

遵循“验收条件先行 -> 最小实现 -> 定向验证 -> 按风险补临时测试”。项目约束要求测试文件不保留，因此：

- 每个高风险核心行为先建立临时 Go/Vitest 测试或假上游反馈环。
- 修复或实现后复跑同一反馈环。
- 测试通过后删除临时测试文件，不把它们纳入最终项目。
- Go 侧执行格式化、静态检查和针对性竞争检查。
- React 侧执行类型检查和正式构建。
- 页面使用可复跑浏览器流程验证功能；视觉验收对比项目自己的 Apple 基线。
- 构建通过不等同于 Codex、Claude Code 或三平台真实运行通过，交付时分别说明验证边界。

## 20. 风险与缓解

| 风险                                       | 影响 | 缓解措施                                                                                                                  |
| ------------------------------------------ | ---- | ------------------------------------------------------------------------------------------------------------------------- |
| SSE 已输出后错误切换造成内容拼接或重复计费 | 高   | 明确提交点，提交后禁止 retry/fallback                                                                                     |
| Responses ID 在不同渠道不兼容              | 高   | 持久化短期渠道亲和，默认不跨渠道切换                                                                                      |
| 列表密钥删除重建后复用主体 ID，继承旧 Responses affinity | 高 | `proxy_keys.id` 使用至少 128 bit 服务端随机不可复用值；物理删除在同一事务清 principal affinity 与密钥行，整包替换先清空 affinity |
| 重试扩大延迟和费用                         | 高   | 次数、渠道数和总时限三重预算，记录重试原因                                                                                |
