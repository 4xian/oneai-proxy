# 本地代理管理平台能力与信息架构调研

> 调研日期：2026-08-31
> 最近同步：2026-08-31
> 调研范围：公开的 One Switch、Sub2API、New API，以及当前 OneAI Proxy 的页面、Go 服务和 SQLite schema。
> 文档定位：外部调研与产品参考，仅用于辅助决策；具体实现以 [`plans/oneai-proxy-solution-plan.md`](../plans/oneai-proxy-solution-plan.md) 为准。
> 说明：用户提到的“subapi”没有给出仓库地址；本文以公开的上游仓库 [Wei-Shaw/sub2api](https://github.com/Wei-Shaw/sub2api) 作为主要参照。其他派生仓库只作为补充，不改变本项目的范围判断。

## 结论摘要

1. OneAI Proxy 的核心应是“渠道（模型和健康策略）+ 全局模型映射 + 请求可观测性 + 运行设置”，而不是复制 New API/Sub2API 的用户、组织、计费或多租户后台。
2. 顶部导航可以保留。当前主入口统一为“概览、渠道、模型、请求、日志、设置”六项；请求记录单独成页，日志页只放操作日志和运行日志。渠道候选规划和探针作为后端/渠道详情能力，不建立独立一级工作流。
3. 渠道管理是当前最大缺口：创建时不应手填 ID，模型应能手动添加或从上游拉取；还需要备注、自定义 Header、并发上限、测试模型、复制、重试与失败自动禁用等闭环。
4. 日志应从低密度卡片改为可筛选的高密度表格，并支持展开或右侧抽屉查看完整 Attempt 链、错误分类、延迟、Token 和四类请求/响应快照；请求正文默认加密保存，管理 API 只遮罩 API 凭证，Cookie 在管理页面显示原值。
5. 当前后端已有健康状态机、冷却、失败阈值、自动禁用、探针运行记录、请求/Attempt 账本、Token 与延迟统计、审计、加密内容 blob、监听设置、配置导入导出以及阶段 10 模型目录与全局映射能力。日志最终重构仍按计划在阶段 6R 单独实施，不能把当前基础代码误认为最终闭环。

## 参照项目

### One Switch

来源：[仓库](https://github.com/yinxulai/one-switch)、[README](https://raw.githubusercontent.com/yinxulai/one-switch/main/README.md)、[页面源码目录](https://github.com/yinxulai/one-switch/tree/main/source/render/source/pages)、[模型队列截图](https://github.com/yinxulai/one-switch/blob/main/snapshot/preview-01.png)、[统计分析截图](https://github.com/yinxulai/one-switch/blob/main/snapshot/preview-02.png)、[请求记录截图](https://github.com/yinxulai/one-switch/blob/main/snapshot/preview-03.png)。

公开 README 明示：它是本地 AI API 网关，支持多个供应商之间故障转移；网络故障、超时、401、403、408、429、5xx 等失败可触发下一个渠道；支持协议感知路由、统一模型名、手动首选和拖拽排序；SSE 流在首个响应开始后不再中途切换；有健康检查、冷却、结构化 Header/JSON Body 修改规则和运行日志。README 还列出请求尝试、成功率、延迟、TTFT、Token、缓存命中、失败原因、模型/协议诊断，以及监听地址、端口、连续失败阈值、冷却时间和流式闲置超时设置。

源码目录显示它把管理台拆成 `overview`、`model-management`、`queue-control`、`request-logs`、`logs`、`access-config`、`modification-rules`、`runtime-settings` 等页面，并将 provider、模型列表、拉取模型选择器、协议端点卡片作为独立组件。概览子组件包含统计卡、趋势、供应商分布、模型排行、延迟分布和失败原因；请求记录包含筛选、表格、详情行和内容抽屉。

对 OneAI Proxy 的借鉴：

- 首页使用少量强业务指标和“待处理事项”引导操作，而不是只展示服务状态。
- 渠道/模型列表使用紧凑表格，行内提供启停、测试、编辑和排序等高频动作。
- 请求详情需要展示完整的 Attempt 链，让用户能解释“为什么切换了渠道”。
- 设置按职责分卡或二级导航组织，避免所有配置挤在一张长表单中。
- One Switch README 所说的默认导出不含 API key 不适用于本项目；OneAI Proxy 已决定使用口令保护的完整加密导出，且完整配置可携带密钥。

### Sub2API

来源：[上游仓库](https://github.com/Wei-Shaw/sub2api)、[README](https://github.com/Wei-Shaw/sub2api/blob/main/README.md)、[中文 README](https://github.com/Wei-Shaw/sub2api/blob/main/README_CN.md)。

Sub2API 是面向 SaaS/订阅分发的多上游账户系统，公开文档列出 OAuth/API Key 账户、用户 API key、token 用量与费用、智能账户调度和 sticky session、每用户/每账户并发限制、请求/token rate limit、Admin dashboard 与 iframe 嵌入，并依赖 Postgres、Redis 等服务。文档还说明 simple mode 可以隐藏 SaaS 功能。

对 OneAI Proxy 的借鉴仅限：并发和限速应有明确归属、管理台应把账户/渠道状态和用量展示清楚。以下能力不纳入本地单用户代理的当前范围：用户、组织、订阅、充值、支付、配额分组、租户隔离、远程账户分发和 Postgres/Redis 依赖。

### New API

来源：[仓库](https://github.com/QuantumNous/new-api)、[中文 README](https://raw.githubusercontent.com/QuantumNous/new-api/main/README.zh_CN.md)、[官方文档](https://docs.newapi.pro/zh/docs)、[功能介绍](https://docs.newapi.pro/zh/docs/guide/wiki/basic-concepts/features-introduction)。

New API 公开文档列出管理控制台、统计、token 分组/模型限制/用户管理、多协议（OpenAI Responses、Realtime、Claude、Gemini、Rerank）、渠道加权随机、失败自动重试和用户级模型限流；失败重试次数位于“设置 → 运营设置 → 通用设置”。文档和版本变更还提到渠道列表手动列宽、日志的流式 timing metrics/task detail，以及渠道/模型测试对话框的紧凑优化。

对 OneAI Proxy 的借鉴：表格密度、可调列宽、紧凑测试弹窗、流式指标和详情视图。不要把 New API 的用户、计费、充值、商业配额、多租户和复杂部署模型带入本地产品。

- [LogsPage.tsx](../web/src/pages/LogsPage.tsx) 已有时间窗口、请求数/fallback/平均延迟/缓存摘要、请求卡片和审计列表；筛选维度和单行详情仍不足，无法高效查看渠道、模型、协议、状态、错误分类和 Attempt 时间线。

### Go 后端和数据模型

- [internal/storage/catalog.go](../internal/storage/catalog.go) 的 `Channel` 已有 ID、名称、备注、分组、协议、Base URL、capabilities、人工状态、健康状态、时间戳、密钥引用、渠道优先级、兜底模型、失败动作和失败阈值，以及自定义 Header、并发上限、请求/流式闲置超时、重试和冷却字段。同协议渠道按 `priority DESC, created_at ASC, id ASC` 生成稳定候选；每个渠道依次匹配原始模型的渠道映射、原始模型的渠道目录、全局映射后的渠道映射、全局映射后的渠道目录，仍未匹配时使用该渠道兜底模型。渠道保存只走 bundle，不再提供独立的行级 POST/PUT。
- 渠道 `capabilities` 为空表示不限制请求能力；只有显式声明能力时才执行能力集合过滤。这样创建渠道时可以不填写能力标签，仍能承接 Responses 的 `input` 或工具请求；需要限制能力时再填写明确的能力集合。
- 能力声明用于描述渠道可承接的请求特征，例如流式、工具调用、视觉、音频或推理；模型资料中的能力只用于展示和筛选，不会把模型库变成代理白名单。
- [internal/server/catalog_api.go](../internal/server/catalog_api.go) 提供渠道 GET/DELETE、聚合 bundle 保存、渠道复制、凭证加密回显、模型发现和未保存渠道即时测试，并支持 `/probe` 和 `/health`；凭证元数据和秘密整体写入系统密钥环，管理 API 仅在明确的编辑会话凭证接口中返回密钥。模型目录、手工模型映射和探针策略由 bundle 聚合保存。
- [internal/storage/sqlite.go](../internal/storage/sqlite.go) 当前 schema version 27 包含渠道优先级、兜底模型、分组、`service_tier` 透传、独立 `channel_models`、跨渠道 `model_catalog`，以及模型映射、探针策略、请求/Attempt、健康运行态、审计、小时聚合、加密正文元数据和 `custom_headers_ignored` 路由事件；`app_settings` 保存监听、完整运行设置和最近模型源地址，令牌 JSON 只保留哈希。上游发现的渠道模型不会自动创建同名模型映射。路由组表已删除。
- [internal/server/proxy.go](../internal/server/proxy.go) 使用结构化 JSON 解析保留请求体全部未知字段，并为选中的渠道替换最终 `model`。渠道开启 `serviceTierPassthrough` 时保留客户端传入的 `service_tier`，关闭时无论客户端是否传入都固定向上游发送 `"default"`。入站请求头先复制，自定义 Header 再按字段覆盖，未填写的原请求头不会被清空。
- [internal/storage/health.go](../internal/storage/health.go) 实现 healthy/degraded/cooldown/half_open/auto_disabled 状态转换、失败计数、指数冷却、Retry-After、阈值后自动禁用、手动重置和健康事件。这个状态机应复用到新的渠道详情页，不应在前端另造状态逻辑。
- [internal/server/probes.go](../internal/server/probes.go) 按渠道探针策略定时调度检查，支持连通性和最小推理；页面级 `/probes` 和 `/probe-policies` 接口已删除。列表「测试」走 `POST /channels/{id}/test` 并写入 `probe_runs`、更新健康；编辑器「测试」走 `POST /channels/test`，不记探针、不改健康。最小推理优先使用渠道模型映射，未配置映射时使用渠道兜底模型。
- [internal/storage/requests.go](../internal/storage/requests.go) 保存逻辑请求和每次 Attempt 的渠道、顺序、状态、错误分类、错误消息、延迟、输入/输出/cache token，并提供请求详情和审计列表；正文单独存为加密 content blob。
- [internal/server/logs_api.go](../internal/server/logs_api.go) 提供请求列表/详情、审计、统计、日志设置、聚合和清理接口。请求列表支持分页、渠道/模型/协议/状态/错误分类/分组/关键词筛选，以及 `from`/`to` 或 `days`（仅 1/7/30，未传默认最近 1 天）；审计列表使用相同的 `days` 规则。
- [internal/config/config.go](../internal/config/config.go) 默认代理监听 `127.0.0.1:9988`、管理监听 `127.0.0.1:9989`，并已有连接、首字节、流式闲置、总超时、最大尝试数和最大 fallback 渠道数，以及日志保留、正文大小、磁盘配额和时区设置。
- [web/src/pages/models/models.tsx](../web/src/pages/models/models.tsx) 与对应 Go/SQLite 接口已实现独立的跨渠道模型目录和标准化模型资料表；支持默认 `models.dev` 源、有限格式预览、选择性同步、来源移除和手工新增。双协议族全局映射在设置页维护。渠道内的 `channel_models` 仍只代表该渠道发现或手工维护的可用模型，不能替代模型资料目录；模型目录只用于展示与输入联想，不限制代理请求。

## 建议信息架构

### 一级导航

保留顶部菜单，但收敛为：

1. **概览**：运行状态、关键指标、异常和快捷操作。
2. **渠道**：渠道列表、模型、健康、容量、测试和复制。
3. **模型**：跨渠道模型资料目录、在线同步预览和手工新增。
4. **请求**：请求记录、Attempt 详情和请求统计切换。
5. **日志**：操作日志和运行日志；运行日志使用独立实时视图。
6. **设置**：设置页内部使用侧边菜单或紧凑分段导航。

模型与探针能力按实际使用位置收敛：

- 全局 `client model -> logical model` 放在设置页的“全局模型映射”，提供两个 JSON 编辑区：OpenAI（同时覆盖 Chat 与 Responses）和 Anthropic（Messages）。每个编辑区内部只填写扁平对象，例如 `{ "modelA": "modelB" }`，不在 JSON 条目中重复写协议。
- `logical model -> upstream model` 放在渠道编辑的“模型”区域。
- 渠道优先级、fallback、重试和失败动作放在渠道编辑页。独立的渠道候选模拟页与 `routes/simulate` 已删除；真实请求仍按协议、渠道模型和优先级选路。
- 探针开关、模式、自动恢复、阈值放在渠道编辑的“探针设置”；探针运行记录在运行日志中查看。独立探针页已删除。

这是 UI 归属和职责收敛：模型页只负责跨渠道模型目录，设置页负责两个协议族的全局映射，渠道编辑页负责渠道级映射；前端不再提供独立的渠道候选或探针一级页面。

### 渠道详情布局

建议一个渠道详情页或抽屉分为四个职责清晰的区域：

- **基础**：名称、可选分组、协议/API 类型、Base URL、备注、人工启停。ID 只读显示，由后端生成，不出现在创建表单。
- **凭证与 Header**：密钥默认遮罩；用户明确操作后才显示和复制，复制后短时清除；支持自定义 Header 键值列表和凭证注入规则。请求内容在数据库中加密，运行日志文件不记录凭证原值，管理 API 只将 API 凭证替换为 `***`。
- **模型**：渠道模型目录支持手动添加或从上游获取，并以可复制、可删除的 Tag 展示；测试模型、添加模型和兜底模型位于同一控制行。手工模型映射作为独立模块维护，不把上游发现结果自动转换为映射。
- **请求设置**：渠道优先级、并发上限、重试次数、连续失败阈值、冷却或自动禁用、兜底模型。展示当前健康状态、失败计数和冷却截止。
- **探针设置**：探针开关、模式、周期、自动恢复和恢复成功阈值；展示最近探针结果。
- **高级设置**：`service_tier` 透传开关等低频选项。关闭时向上游固定发送 `default`，开启时原样透传客户端值。

详情页动作：保存、模型配置中的单模型即时测试、复制渠道、手动探针、重置健康、启用/禁用、删除。模型即时测试直接使用当前表单的协议、Base URL、凭证、自定义 Header 和所选模型，无需先保存；复制必须由后端生成新 ID。

### 模型管理页面

模型页面是跨渠道的资料管理工作台，不是代理白名单或请求转发配置入口。页面只承载模型目录；全局映射已移到设置页。模型目录内部表格滚动，页面本身不因模型数量增加产生额外纵向滚动。模型目录支持分页、表头拖拽列宽和固定操作列，按模型 ID/显示名称/厂商搜索，按协议、厂商、模型类型、能力和来源筛选，并提供同步预览、新增模型和删除失效模型动作。

模型目录保存标准化模型资料：模型 ID、显示名称、基础模型、厂商、服务供应商、协议、文本/图像/音频等模型类型、输入输出模态、能力、上下文与最大输出、费用及计费单位、来源和同步状态。费用只用于展示和未来统计，不参与计费、排序或请求转发。同一基础模型的多个供应商版本在详情中分开显示，不能合并成一个实际请求模型。

在线同步默认使用公开的 `https://models.dev/catalog.json`。同步必须经过“请求并解析 → 预览差异 → 搜索/筛选并选择 → 用户确认 → 事务写入”流程；支持 models.dev、OpenAI `data[].id`、常见 `models[].id` 和 CCH Plus `model_name/slug` 四种明确适配器。未知结构直接报格式错误，不从任意嵌套字段猜测。远端已移除只在相同来源 URL 与相同 Adapter 的两次同步之间计算，先标记失效，再由用户确认后选择性删除；手工新增记录不受在线同步覆盖。

手工新增使用弹窗而不是 JSON 导入，模型 ID、协议为必填，显示名称可选且缺失时使用模型 ID 展示，其余资料与费用字段可选。渠道编辑中的模型联想只按当前渠道协议过滤，并对模型 ID 和显示名称做文字模糊匹配；不按能力、厂商或模型类型过滤，不显示全部模型，也不以模型目录限制代理请求。无明确协议的在线记录只在模型页展示，不进入联想结果。

全局映射在设置页的“全局模型映射”提供两个 JSON 编辑器：OpenAI 和 Anthropic；每个编辑器的内容固定为 `{ "modelA": "modelB" }`，空值显示 `{}`。OpenAI 编辑器同时服务 `openai_chat` 与 `openai_responses`，Anthropic 编辑器服务 `anthropic_messages`。目标模型不要求存在模型目录；运行时只做一次 `A -> B` 查询，不继续执行 `B -> C`。保存时拒绝空键、空值、非字符串、自映射、重复键和嵌套协议对象，并与渠道映射保持“渠道优先于全局”的既有解析顺序。

### 渠道字段决策

| 字段 | 创建/编辑 | 当前判断 |
| --- | --- | --- |
| ID | 只读 | 后端自增或生成不可重复 ID，不让用户填写 |
| 显示名称 | 必填 | 保留 |
| 分组 | 可选 | 用于管理筛选；代理按分组选择需先定义客户端指定分组的请求约定 |
| 协议/API 类型 | 必填 | 保留，可用预设减少手填 |
| Base URL | 必填 | 填上游 API 根地址，可包含上游要求的 `/v1`；适配器会规范化并避免重复拼接，不能填本地代理地址 |
| 密钥 | 创建必填，编辑可替换 | 默认遮罩；显式回显/复制需本地安全交互 |
| 模型 | 创建/编辑 | 模型目录支持手动添加 + 上游发现；逻辑模型/上游模型只在手工映射区维护 |
| 备注 | 创建/编辑 | 新增，用于运维说明 |
| 自定义 Header | 创建/编辑 | 使用 JSON 对象按字段覆盖；只覆盖填写的 Header，不替换整套原始请求头 |
| 渠道优先级 | 创建/编辑 | 数值越大越先调用；同优先级按创建时间和 ID 稳定排序 |
| 并发上限 | 创建/编辑 | 新增；先按渠道，后续再考虑按模型 |
| 重试次数 | 创建/编辑 | 新增；与全局预算共同决定实际尝试次数 |
| 失败动作/阈值 | 创建/编辑 | 复用已有 `failure_action`/`failure_threshold` |
| 兜底模型 | 创建/编辑 | 客户端模型未命中该渠道映射时使用；未配置则跳过该渠道 |
| 探针 | 创建/编辑 | 迁移已有 ProbePolicy，避免独立页面重复配置 |
| `service_tier` 透传 | 高级 | 关闭时向上游固定传 `default`，开启时原样透传客户端值 |
| capabilities 逗号文本 | 高级 | 不作为主要字段；可由协议/模型推导，必要时改为多选 |

密钥回显和复制是用户明确需要的高风险操作：默认只显示遮罩值，回显前要求再次确认或本地管理员认证，复制按钮应提供短时清除提示；导出仍使用完整配置加密，操作审计和运行日志不得写入凭证原值。请求详情中的 Cookie 在管理页面显示原值，但数据库中的整条请求快照仍然加密保存。

## 概览页应有的内容

首屏按“现在是否可用、哪里需要处理、下一步做什么”排序：

- 服务状态、代理/管理监听地址、当前运行时间和配置变更提示。
- 今日请求、成功率、fallback 率、平均延迟/TTFT、输入/输出/cache token、当前并发与上限（实现并发后）。
- 健康渠道、冷却中、自动禁用、人工禁用、缺少凭证、无模型映射的数量，并可直接进入渠道详情。
- 请求趋势和失败原因分布；渠道/模型使用排行。
- 异常状态在渠道健康表和日志中呈现，并提供进入渠道编辑或完整日志的操作；不额外设置黄色告警条，避免与表格状态重复。
- 最近请求表可直接跳转日志详情，至少显示时间、客户端模型、最终状态、Attempt 次数、延迟和 token。
- 无渠道时显示单一主 CTA“新增渠道”，创建完成后引导配置模型并测试。

页面应保持 Apple 风格的材料、字体和动效变量，但采用管理台的紧凑信息层级、表格和操作密度；不要用营销式大 Hero 或装饰性卡片堆叠。

## 日志与可观测性建议

### 列表和筛选

请求列表使用一条客户端请求一行的高密度表格，默认显示请求时间、原始渠道名称、模型映射、状态 Tag、协议、分组、输入/输出/缓存/思考/总 Token、缓存率、TTFT、TPS、耗时和详情。发生重试时在原始渠道名称旁显示标记，悬浮展示渠道链路。支持时间、模型、协议、状态、渠道、分组、错误分类、fallback 和关键词筛选；默认每页 50 条，可选 20/50/100，列显隐只缓存在浏览器本地，不新增诊断日志模式。

操作日志单独展示，使用时间、操作类型、目标、结果、操作 IP 和操作者字段；运行日志使用独立实时视图。顶部统一使用“概览、渠道、模型、请求、日志、设置”导航，请求记录不再嵌入日志页，日志页只区分操作日志和运行日志。

### 请求详情

详情从右侧抽屉打开，顶部显示请求 ID、协议、原始/逻辑/最终模型、首次/最终渠道、分组、状态、时间、耗时、TTFT、TPS 和 Token。下方按 Attempt 时间线展示每次渠道、上游模型、HTTP 状态、错误分类、错误摘要、重试/切换原因和时间点。客户端请求、每个 Attempt 上游请求/响应、最终客户端响应四类 Header/Body 区块默认折叠，正文默认加密保存；API Key 显示 `***`，Cookie 在页面显示原值。

当前 [requests.go](../internal/storage/requests.go) 和 [logs_api.go](../internal/server/logs_api.go) 已完成阶段 6R 的最终日志契约；筛选、分页、操作 IP、运行日志文件/SSE、完整字段和最终详情交互均以权威计划中的最终实现为准。

## 设置页建议

设置内部采用侧边菜单或固定宽度的二级导航，建议分为：

- **通用**：时区、默认协议和界面主题。
- **监听与访问**：代理/管理 IP 与端口、管理令牌、代理令牌；保存后提示重启生效。
- **请求与故障转移**：连接/首字节/流式闲置/总超时、最大尝试和 fallback 渠道预算。
- **日志与存储**：请求/响应正文各自大小上限、请求/操作/运行日志分别保留天数、磁盘配额、运行日志文件轮转、聚合和清理。
- **配置与恢复**：口令保护的完整加密导出/导入、差异预览、备份、诊断摘要、校验和恢复。
- **高级**：仅放不常用的 Header/Body 修改规则和调试模拟，不污染日常工作流。

已有完整配置导入/导出语义必须保持：配置整体加密，导入后替换对应配置即可使用；日志明细不导出。导入写入应用当前 SQLite，不接受 SQL 文件作为配置格式；完整数据库备份另行保存 SQLite 一致性快照、加密正文文件和清单，用于整机恢复。令牌哈希保存在本地数据库，明文放在与渠道凭证相同的秘密存储中；首次启动由应用写入默认值。

### 配置迁移与数据库备份边界（当前实现）

当前配置导出格式为 `schemaVersion: 8`。`safe` 和 `complete_encrypted` 导出的配置范围相同，包含渠道基本配置、渠道模型目录、跨渠道 `modelCatalog`、全局模型映射、渠道模型映射、探针策略，以及监听地址/端口、请求策略、日志设置、时区和最近模型源地址；`complete_encrypted` 另外在口令加密载荷中携带渠道凭证、管理令牌和代理令牌。旧包中的 `routeGroups` 会被忽略，不报错、不写入。模型目录、来源状态和两个协议族映射已纳入校验与事务导入。

配置导入不是数据库合并，而是“解析/解密 → Schema 与语义校验 → 差异预览 → 自动完整备份 → 单事务替换可迁移配置”。替换会更新或重建渠道及其配置子表，渠道模型、渠道映射和探针策略也按导入文件中的内容替换。独立的 `requests` 主记录、`hourly_metrics`、`audit_logs`、`content_blobs` 元数据和正文文件不会由配置导入恢复，也不会因这次配置替换被直接删除；但被清理 Attempt 的请求详情可能不再有 Attempt 链。`safe` 不包含任何凭证或令牌，导入后渠道需要重新配置凭证才能参与代理；`complete_encrypted` 导入后会恢复凭证和两类令牌，可以直接使用。

完整数据库备份是独立接口生成的 SQLite 一致性快照，恢复时会替换当前 schema 中的全部应用表：配置、模型目录、请求/Attempt、健康与探针记录、审计、小时聚合、Responses 亲和记录和正文元数据，并复制加密正文文件。备份不包含系统密钥环中的渠道密钥、正文密钥或主密钥明文；跨电脑迁移不能只恢复该备份，必须同时使用 `complete_encrypted` 配置导出恢复秘密。换句话说，配置导入不会把所有数据库数据导入，配置导出也不会导出所有数据库数据；需要整库历史时使用完整备份，需要跨电脑直接使用配置时使用完整加密配置导出。

### 阶段 11 跨平台完整迁移包规划

现有 `safe`、`complete_encrypted` 和完整数据库备份分别服务于配置分享、加密配置恢复和整机灾备；它们不等同于面向不同电脑/操作系统的“一键迁移”。后续新增独立的 `oneai-proxy-migration` 单文件格式：用户使用一次口令导出，目标机选择文件、预览并确认后即可导入，按要求重启后直接使用，不需要复制 SQLite、源机密钥环、配置文件或 SQL。

迁移包整体采用 gzip + Argon2id + XChaCha20-Poly1305 加密，载荷只包含当前可迁移配置、渠道凭证、管理令牌、代理令牌、模型目录和全局/渠道映射；目标机为渠道凭证重新写入本地密钥环并生成新的 `secret_ref`。迁移包明确排除并且不覆盖 `requests`、`attempts`、健康运行态、探针运行、Responses 亲和、审计、统计、正文元数据、正文文件、WAL/SHM、缓存和日志。导入前进行版本/语义校验和脱敏预览，确认后才创建回滚快照并执行密钥环暂存与 SQLite 单事务替换；错误口令、篡改包、版本不兼容或任一步写入失败都必须清理暂存秘密并保持原配置及目标机日志不变。

## 分阶段落地建议

1. **信息架构与契约**：确定六个一级入口、渠道详情区域、字段和 API 兼容策略；先画出空状态、加载、错误和无模型状态。
2. **渠道闭环**：自动 ID、模型手动/发现、渠道模型绑定、备注/Header、并发字段、测试、复制、显式凭证回显/复制。
3. **健康与故障**：把已有 ProbePolicy/health 状态机移入渠道详情，补充重试预算、自动禁用和冷却信息展示；验证手动探针、定时探针和重置健康。
4. **可观测性**：扩展日志查询筛选和摘要，重做请求表/详情 Attempt 时间线，补充 TTFT/TPS 等确有数据来源的指标。
5. **模型目录与全局映射**：阶段 10 已完成模型标准化、在线源预览与选择性同步、失效删除、手工新增、OpenAI/Anthropic 双编辑区、渠道模型联想和导入导出版本升级；后续只维护来源兼容性。
6. **概览和设置细节**：接入趋势、异常行动区、模型排行和设置二级菜单；完成暗色/亮色、响应式、无偏移和 Semi 组件视觉验收。
7. **高级能力评估**：只有在 P0/P1 稳定后，再讨论多 key 轮换、权重、结构化修改规则和更复杂的候选诊断。

## 不纳入当前范围

不引入 Sub2API/New API 的用户注册、组织/租户、订阅、支付、充值、商业计费、配额套餐、远程账户池、iframe 外部系统和强制 Postgres/Redis 部署。它们会把本地单用户代理变成 SaaS 管理平台，既增加部署成本，也偏离当前“本机浏览器管理 + 本地代理转发”的目标。

## 实施验收边界

### P0 验收

完成一个渠道后，应能在同一条管理流程中填写基本信息、凭证、模型、优先级、并发与故障策略，获取或手工添加模型，选择测试模型并执行真实测试。保存后概览页应立即显示渠道和健康状态；代理请求按渠道优先级选择候选，渠道映射优先于全局映射，未匹配时使用该渠道兜底模型。复制渠道必须生成新的渠道 ID，不能覆盖原渠道。

### P1 验收

一条发生重试或 fallback 的请求，应能在日志详情中还原候选顺序、每次 Attempt、HTTP 状态、错误分类、切换原因和最终结果。请求和响应正文默认保存为加密快照，超出各自 `1 MiB` 上限时标记截断；筛选条件应能定位到渠道、模型、协议、状态和 fallback 请求。

### 模型管理验收

模型目录同步必须能对默认 models.dev 和三种兼容目录格式完成预览、协议归类、能力/模态/费用展示、差异计算和选择性写入；未知格式、无效协议、重复稳定键和非法费用必须明确失败且不产生部分写入。来源已移除记录只能在用户确认后删除，且不得影响渠道模型、渠道映射、全局映射或日志。渠道模型联想只返回当前协议的名称模糊匹配，模型目录不能成为代理白名单。全局映射提供 OpenAI 与 Anthropic 两个 JSON 编辑区，每个编辑区都是扁平 `{ "modelA": "modelB" }` 对象，默认 `{}`，单次解析并拒绝非法值；完整加密配置导出和导入需携带模型目录与映射，导入失败完整回滚。

### 页面质量验收

每个页面完成后都要执行类型检查、构建和浏览器回归，覆盖加载、空数据、失败、禁用和成功状态；同时检查控制台错误、元素偏移、移动端溢出、明暗主题对比度以及 Semi 组件默认交互态。前端布局继续使用 flex，禁止 `grid` 和 `gap`。
